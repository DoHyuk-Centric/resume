# 이력서 피드백 정리

> 대상: `resume.html`의 소개 및 프로젝트 영역  
> 출처: `info/reeca첨삭.pdf`, `info/권태하매니저피드백.md`, `info/김기수멘토링피드백.md`, `info/김성박강사의피드백.md`, `info/최종프로젝트 평가 피드백.pdf`  
> 정리 기준: 1~5장은 소개 문구, 6장부터는 프로젝트 수정에 공통으로 적용할 피드백을 수록

## 1. REECA 첨삭

출처: `info/reeca첨삭.pdf` 4페이지, `Introduction` 영역

### 당시 소개 첫 문장

> React·Next.js 기반으로 팀 프로젝트 1개와 개인 프로젝트 3개를 완성한 프론트엔드 개발자입니다.

### REECA 수정 예시

> React·Next.js 기반 프론트엔드 개발자로, 마크다운 렌더링 npm 패키지를 직접 개발·배포하고 부트캠프 파이널 프로젝트에서 팀 1위를 달성했습니다.

### 첫 문장에 대한 피드백

- 프로젝트 개수 나열만으로는 차별화된 강점을 전달하기 어렵다.
- 첫 문장은 `가장 차별화된 핵심 역량 + 대표 성과 1개`로 압축해야 한다.
- 기술 스택과 npm 패키지 배포 또는 부트캠프 1위 같은 대표 성과를 한 줄에 담는 방식을 권장한다.

### 당시 소개 마지막 문장

> 설계 문서·코드 리뷰에 AI 도구를 역할별로 분리 운용해 팀의 개발 기간을 단축한 경험이 있으며, 문제를 만나면 원인을 실측으로 특정하고 문서로 남기는 개발자를 지향합니다.

### REECA 수정 예시

> AI 도구를 역할별로 분리 운용해 설계·리뷰 사이클을 단축했으며(근거 미제시), 장애 원인을 실측 후 문서화해 재발을 방지한 경험이 있습니다.

### 마지막 문장에 대한 피드백

- `개발 기간을 단축`했다는 표현에는 구체적인 전후 수치가 없어 설득력이 약하다.
- 기간 단축을 유지하려면 `2주→10일`, `−30%`처럼 정량 근거를 추가해야 한다.
- 정량 근거가 없다면 해당 효과를 삭제하거나 근거가 부족하다는 점을 명확히 해야 한다.
- `지향합니다`는 추상적인 선언이므로 실제 행동과 결과로 바꾸는 것이 좋다.

## 2. 권태하 매니저 피드백

출처: `info/권태하매니저피드백.md`

### 이력서 소개에 대한 피드백

> 소개 부분 내용에 있어 Kanto에서 실시간 채팅·관리자 권한 체계를 구현해 전체 5개 팀 중 1위를 기록한 부분을 좀 더 명확하게 기술하고, 기술 스택 내용도 추가하면 좋을 듯함. 예: API 설계 및 연동 등을 바탕으로 실시간 채팅·관리자 권한 체계를 구현.

정리:

- `실시간 채팅·관리자 권한 체계를 구현했다`는 결과만 적지 말고 어떤 기술적 방법을 사용했는지 보여줘야 한다.
- API 설계·연동 등 구현 근거를 소개 문장에 추가하는 방안을 제안했다.
- 팀 1위와 본인의 기술적 기여 사이의 연결을 더 명확히 해야 한다.

### 소개 문구와 포트폴리오 근거의 연결에 대한 피드백

> 이력서 소개 내용에서 `설계 문서·코드 리뷰에 AI 도구를 역할별로 분리 운용해 팀의 개발 기간을 단축한 경험이 있으며` 부분을 확인할 수 있는 내용이 포트폴리오에서 보이지 않음.

정리:

- 소개에서 주장한 내용은 포트폴리오에서 확인할 수 있어야 한다.
- 근거를 포트폴리오에서 제시할 수 없다면 소개에서 해당 주장을 제거하거나 표현을 낮춰야 한다.

## 3. 김기수 멘토 피드백

출처: `info/김기수멘토링피드백.md`

### 긍정적으로 평가한 부분

> 소개 부분에 적어주신 `원인을 실측으로 특정하고 문서로 남기는 개발자`라는 문장도 이력서 전체 내용과 잘 어울려서 지원자의 개발 스타일이 자연스럽게 전달되었습니다.

정리:

- `실측으로 원인을 찾는다`는 방향은 프로젝트 내용과 잘 맞는다.
- 소개가 지원자의 개발 방식을 보여준다는 점은 유지할 가치가 있다.

### 소개 길이에 대한 피드백

> 소개가 생각보다 길어서 처음 읽는 사람이 핵심을 한 번에 파악하기 어려울 수도 있습니다. 강점만 조금 더 압축해서 보여주면 첫인상이 더 좋아질 것 같습니다.

정리:

- 소개가 길어 핵심을 즉시 파악하기 어렵다.
- 강점을 압축해 첫인상을 개선해야 한다.

### AI 표현에 대한 피드백

> AI 관련 경험이 여러 프로젝트에서 반복해서 등장하는데, 요즘은 AI를 활용한 경험 자체보다는 AI를 활용해서 어떤 문제를 해결했는지를 더 중요하게 보는 경우가 많습니다. 그래서 AI라는 키워드보다는 성능 개선이나 개발 효율 향상 같은 결과를 조금 더 강조하면 오히려 더 설득력 있게 느껴질 것 같습니다.

정리:

- AI를 사용했다는 사실 자체는 강한 차별점이 아니다.
- AI 키워드보다 해결한 문제와 결과를 강조해야 한다.
- 성능 개선 또는 개발 효율 향상처럼 검증 가능한 결과가 중심이 되어야 한다.

## 4. 세 피드백의 공통 요구사항

아래 내용은 세 피드백을 종합한 해석이며 피드백 원문은 아닙니다.

1. 소개는 짧고 즉시 이해되어야 한다.
2. 프로젝트 개수보다 대표 성과를 먼저 보여줘야 한다.
3. Kanto 1위와 본인의 구체적인 기술 기여를 연결해야 한다.
4. `실측으로 원인을 찾는 개발자`라는 정체성은 유지할 가치가 있다.
5. 근거 없는 `개발 기간 단축`과 같은 표현은 사용하지 않아야 한다.
6. AI라는 도구보다 AI 또는 기술을 사용해 해결한 문제와 결과를 강조해야 한다.
7. 소개에서 주장한 내용은 이력서 프로젝트 항목이나 포트폴리오에서 확인할 수 있어야 한다.

## 5. 소개 수정 시 판단해야 할 핵심 쟁점

1. 첫 문장의 중심을 `Kanto 팀 1위`, `npm 패키지 개발·배포`, `실측 기반 문제 해결` 중 어디에 둘 것인가?
2. 권태하 매니저가 제안한 API 설계·연동 같은 기술적 구현 근거를 소개에 어느 정도까지 넣을 것인가?
3. 84%·83%·8.2배 세 수치를 모두 유지할 것인가, 가장 강한 수치만 남길 것인가?
4. `실측으로 병목을 좁히고 재발 방지까지 연결한다`는 문장을 핵심 정체성으로 유지할 것인가?
5. 소개를 한 문단으로 만들 것인가, 현재처럼 정체성과 성과를 두 문단으로 나눌 것인가?

## 6. 프로젝트 수정 시 공통 요구사항

아래 내용은 `info` 폴더의 첨삭과 피드백에서 프로젝트와 관련해 반복된 요구를 합친 것입니다. 특정 피드백의 문장을 그대로 옮긴 것이 아니라, 실제 이력서 수정에 적용할 수 있도록 공통 기준으로 재구성했습니다.

### 요구사항 1. 프로젝트마다 대표 성과를 하나 먼저 보여준다

- 모든 프로젝트를 같은 분량과 형식으로 나열하면 뒤로 갈수록 반복적으로 보인다.
- 프로젝트별로 가장 자신 있는 성과 하나를 먼저 정하고, 나머지 내용은 그 성과를 설명하는 근거로 사용한다.
- Kanto는 대표 프로젝트로 가장 구체적으로 작성하고, 개인 프로젝트는 서로 다른 강점이 보이도록 압축한다.

출처 근거:

- 김기수 멘토: 프로젝트마다 가장 자신 있는 성과 하나를 중심으로 차별화할 것을 제안
- 김성박 강사: Kanto를 대표작으로 크게 세우고 나머지 프로젝트는 압축할 것을 제안
- REECA 5페이지: 담당 영역 나열보다 핵심 기여 1~2가지와 결과로 압축할 것을 제안

### 요구사항 2. 서비스 설명은 한 줄로 끝내고 바로 본인 기여로 전환한다

- 첫 문장은 누가 사용하는 어떤 서비스인지 한 줄로 설명한다.
- 이후에는 기능 전체가 아니라 본인이 맡아 설계·구현·개선한 내용을 적는다.
- 채용 담당자가 서비스 소개보다 본인의 기여를 먼저 파악할 수 있어야 한다.

권장 순서:

> 서비스 한 줄 요약 → 본인이 해결한 핵심 문제 → 행동과 기술 선택 → 검증된 결과

출처 근거:

- REECA 5페이지: 서비스 소개를 한 줄로 축약하고 곧바로 본인 기여와 성과로 전환할 것을 요구
- 권태하 매니저: 담당 결과뿐 아니라 API 설계·연동 등 기술적 구현 근거를 함께 제시할 것을 요구

### 요구사항 3. 기능을 나열하지 말고 `문제 → 판단 → 해결 → 결과`로 작성한다

- 무엇을 만들었는지만 나열하지 않는다.
- 어떤 문제가 발생했는지, 무엇을 기준으로 원인을 판단했는지, 왜 해당 해결 방법을 선택했는지 보여준다.
- 이력서에서는 위 과정을 한 문장 또는 두 문장으로 압축한다.
- 자세한 재현 과정과 대안 비교는 포트폴리오에서 설명한다.

권장 문장 구조:

> `[문제 상황]`을 `[측정·분석 방법]`으로 진단 → `[선택한 해결 방법과 이유]`를 적용해 `[검증 결과]`

출처 근거:

- REECA 6·7·9페이지: Problem→Solution→Result를 한 문단으로 통합할 것을 반복해서 제안
- 권태하 매니저: 문제 인지, 정리, 우선순위 설정, 의견 취합과 해결 접근 과정이 필요하다고 지적
- 김기수 멘토: 문제 발견과 원인 분석, 해결 방법 적용 과정이 현재 이력서의 강점이라고 평가

### 요구사항 4. 수치는 측정 조건과 범위를 함께 검증한다

- 전후 수치만 쓰지 말고 가능한 경우 측정 도구, 데이터 범위, 기간 또는 동일 조건을 명시한다.
- `성능 점수` 대신 `Lighthouse Performance`처럼 측정 도구를 밝힌다.
- 일회성 총량인지 월간 사용량인지 확인되지 않은 수치에 임의로 기간을 붙이지 않는다.
- 개선 전후 측정값이 없다면 `개선`이나 `향상`을 단정하지 않고 `적용`, `구현`, `점검`처럼 확인 가능한 행동만 적는다.

출처 근거:

- REECA 6페이지: 390MB→64MB 수치의 기간과 영향 범위를 명시할 것을 요구
- REECA 6·10페이지: LCP 등 개선 전후 값과 Lighthouse 같은 측정 도구를 명확히 할 것을 요구
- REECA 9페이지: npm 패키지의 baseline, 개선 후 값과 비교 수치를 한 줄에 함께 제시할 것을 제안

### 요구사항 5. 기술 이름보다 선택 이유와 결과를 보여준다

- 프로젝트마다 기술 스택을 길게 반복하지 않는다.
- 기술을 적을 때는 `왜 선택했는지` 또는 `무엇이 달라졌는지`와 연결한다.
- Git·GitHub·npm·ESLint·Vite처럼 기본 도구는 핵심 기여가 아니라면 축약하거나 별도 기술 스택 영역에 맡긴다.
- 프로젝트 본문에는 문제 해결에 실제로 중요한 기술 1~2개만 남긴다.

출처 근거:

- REECA 7~9페이지: 단순 기술 스택 나열은 Skills 섹션과 중복되므로 핵심 기술과 적용 맥락만 남길 것을 반복해서 요구
- 권태하 매니저: 기술 스택 자체보다 어떤 설계와 연동을 바탕으로 기능을 구현했는지 보여줄 것을 제안

### 요구사항 6. 팀 성과와 개인 기여를 명확하게 분리한다

- `파이널 프로젝트 1위`, `총점 96점`, `기술 구현·완성도 40/40`은 팀의 결과로 표기한다.
- 팀 결과 바로 앞에 본인이 소유한 기능이나 해결한 문제를 배치해 기여 관계를 보여준다.
- 실제로 주도한 작업에는 `참여`보다 `설계`, `구현`, `구축`, `개선`처럼 범위가 분명한 동사를 사용한다.
- 반대로 팀 전체가 수행한 테스트·문서·리뷰 성과를 개인이 모두 수행한 것처럼 표현하지 않는다.

표현 예시:

> Supabase Realtime 기반 1:1 채팅을 구현하고 운영 안정성을 보강해, 팀이 기술 구현·완성도 40/40과 총점 96점으로 파이널 프로젝트 1위를 기록하는 데 기여

출처 근거:

- 권태하 매니저: Kanto 1위와 본인의 기술적 기여 사이의 연결을 명확히 할 것을 요구
- 김성박 강사: 1위 결과만 제시하지 말고 구조를 잡고 팀을 운영한 역할 서사를 살릴 것을 제안
- 최종프로젝트 평가: 96점과 각 평가 항목은 팀 전체 결과이며, 협업 항목은 리뷰가 품질 관문으로 충분히 작동하지 않아 16/20을 받음

### 요구사항 7. 협업은 별도 활동이 아니라 문제 해결 과정 안에서 보여준다

- 일정 관리·주간 보고서·리뷰 문서를 만들었다는 사실만 적지 않는다.
- 문제가 발생했을 때 어떻게 공유하고, 담당자와 우선순위를 정하고, 의견을 모아 해결까지 연결했는지 설명한다.
- 리뷰 개수보다 리뷰가 실제 수정과 품질 향상으로 이어진 사례를 우선한다.
- Kanto의 리뷰 체계를 완벽한 품질 관문으로 구축했다고 과장하지 않는다.

출처 근거:

- 권태하 매니저: 기술적 해결과 팀워크가 분리되어 보이며, 문제 상황에서 일정·보고 체계를 어떻게 활용했는지 필요하다고 지적
- 김성박 강사: 주간 보고서와 일정을 운영하며 팀이 움직이도록 한 역할을 드러낼 것을 제안
- 최종프로젝트 평가: Git Flow와 리뷰 참여는 좋았지만 실제 외부 의견이 남은 병합이 적어 리뷰 품질 관문이 부족했다고 평가

### 요구사항 8. AI 사용 여부보다 해결한 문제와 검증 결과를 적는다

- `AI를 사용했다`는 사실만으로 성과를 만들지 않는다.
- AI가 시뮬레이션, 설계 검토, 문서화 또는 코드 리뷰 중 어떤 역할을 했는지 범위를 한정한다.
- AI 활용 결과를 수치나 산출물로 확인할 수 없다면 핵심 성과가 아니라 보조 방법으로만 표현한다.

출처 근거:

- 김기수 멘토: AI 경험 자체보다 AI로 어떤 문제를 해결했는지를 강조할 것을 제안
- REECA 4페이지: 근거가 없는 개발 기간 단축 표현을 삭제하거나 정량화할 것을 요구
- 권태하 매니저: 이력서에서 주장한 AI 활용 효과가 포트폴리오에서 확인되지 않는다고 지적

### 요구사항 9. 결과를 직접 확인할 수 있는 근거를 연결한다

- 프로젝트명에는 배포 링크를, 마지막에는 GitHub 저장소를 연결한다.
- npm 패키지는 npm 페이지, 문서화 프로젝트는 실제 문서 또는 관련 PR·이슈를 연결한다.
- 다운로드 수, GitHub Star, 방문 수, 사용자 반응처럼 외부 검증 지표가 실제로 있다면 추가한다.
- 존재하지 않거나 의미가 작은 지표를 억지로 만들지 않는다.

출처 근거:

- 김기수 멘토: 각 프로젝트에 GitHub 저장소와 배포 링크를 제공할 것을 제안
- REECA 2·8~10페이지: npm 다운로드, GitHub Star, 번역 문서 수, 접근 통계, PR·이슈 링크 같은 외부 검증 지표를 제안

### 요구사항 10. 소개·이력서·포트폴리오의 사실과 수치를 일치시킨다

- 소개에서 주장한 강점은 프로젝트 항목 또는 포트폴리오에서 확인할 수 있어야 한다.
- 같은 성과의 명칭, 수치, 측정 조건을 문서마다 다르게 쓰지 않는다.
- 이력서는 결론과 결과를 보여주고, 포트폴리오는 그 결론에 도달한 과정을 증명한다.
- 이력서에 없는 세부 사례가 포트폴리오에 있는 것은 괜찮지만 서로 모순되면 안 된다.

출처 근거:

- 권태하 매니저: 소개의 AI 활용 및 기간 단축 주장을 포트폴리오에서 확인할 수 없다고 지적
- REECA 10페이지: 소개의 8.2배 성과를 npm 패키지 프로젝트에서도 같은 기준으로 표기할 것을 요구

## 7. 프로젝트별로 반드시 같을 필요가 없는 항목

공통 요구사항은 모든 프로젝트를 똑같이 만드는 규칙이 아닙니다. 다음 항목은 프로젝트 성격에 맞춰 다르게 적용합니다.

| 프로젝트 유형 | 우선해서 보여줄 내용 |
|---|---|
| 팀 프로젝트 | 본인 소유 기능, 협업 속 문제 해결, 팀 결과에 대한 기여 |
| 성능 개선 프로젝트 | 측정 조건, 병목 진단, 개선 전후 수치 |
| 도구·패키지 프로젝트 | 해결하려는 개발 문제, API·구조 설계, 배포 및 외부 사용 근거 |
| 문서화 프로젝트 | 실제 제작 범위, 자동 검증, 사용자 접근 또는 외부 반응 |
| 학습 목적 프로젝트 | 기술을 선택한 이유와 학습이 실제 구현 결과로 이어진 근거 |

## 8. 현재 이력서에 적용할 공통 문장 틀

모든 문장을 같은 모양으로 만들 필요는 없지만, 초안을 검토할 때 다음 틀을 사용할 수 있습니다.

### 문제 해결형

> `[발견한 문제]`를 `[측정·분석 방법]`으로 원인 특정 → `[해결 방법]`을 적용해 `[검증 결과]`

### 기능 소유형

> `[핵심 기능]`의 `[설계 범위]`부터 `[운영·예외 처리 범위]`까지 구현

### 협업 기여형

> `[발생한 팀 문제]`를 공유하고 `[담당·우선순위·기준]`을 정리해 `[완료 또는 품질 결과]`로 연결

### 기술 선택형

> `[제약 또는 목표]` 때문에 `[기술·구조]`를 선택해 `[확인된 결과]`를 달성

## 9. 프로젝트 수정 전 최종 점검표

- [ ] 서비스 설명이 한 줄 이내인가?
- [ ] 담당 기능을 모두 나열하지 않고 대표 기여 1~2개를 선택했는가?
- [ ] 본인의 행동과 팀 전체 결과가 구분되어 있는가?
- [ ] 문제와 기술 선택 이유가 드러나는가?
- [ ] 수치에 측정 도구·조건·범위가 필요한지 확인했는가?
- [ ] 근거가 없는 향상·단축·효율 표현을 제거했는가?
- [ ] AI보다 AI로 해결한 문제와 결과가 먼저 보이는가?
- [ ] 단순 기술 스택 나열이 본문을 차지하지 않는가?
- [ ] 소개와 동일한 성과의 명칭·수치가 일치하는가?
- [ ] GitHub·배포·npm·문서 등 확인 가능한 링크가 있는가?
- [ ] 다른 프로젝트와 구분되는 대표 강점이 있는가?
- [ ] 이력서에서 생략한 과정이 포트폴리오에서 확인 가능한가?

## 10. Kanto 표현에서 별도로 검증할 범위

Kanto는 팀 성과와 개인 작업이 넓게 섞여 있으므로 다음 표현은 적용 전에 근거 범위를 다시 확인합니다.

1. `파이널 프로젝트 1위`, `총점 96점`, `기술 구현·완성도 40/40`은 개인 점수가 아니라 팀 결과다.
2. 실시간 1:1 채팅, 관리자 기능, 공지사항, SEO, 인증 보안 중 본인이 직접 설계·구현한 범위를 기능별로 구분한다.
3. E2E·API 통합 테스트, CI, ESLint 개선처럼 팀원이 주도한 작업은 개인 성과로 가져오지 않는다.
4. 저장소에 멘토 리뷰 문서가 20회 이상 존재하는 것과 본인이 모든 리뷰를 담당자·우선순위별로 재구성한 것은 다른 주장이다. 실제로 직접 정리한 범위를 확인한 뒤 숫자를 사용한다.
5. PR 병합과 충돌 해결은 통합 기여로 사용할 수 있지만, 병합 개수를 작성 코드량이나 리뷰 품질과 동일하게 해석하지 않는다.
