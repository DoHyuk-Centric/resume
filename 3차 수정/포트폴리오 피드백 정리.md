## 1. 피드백 출처별 포트폴리오 요구사항

### 1.1 REECA 첨삭

REECA 첨삭은 이력서 문장에 대한 의견이 중심이지만, 다음 항목은 포트폴리오가 이력서의 근거 역할을 하기 위해 반드시 반영해야 합니다.

- 기능과 기술 스택을 나열하지 말고 `문제 → 해결 → 결과`로 통합한다.
- 성능 수치에는 측정 도구·조건·범위·기간을 함께 제시한다.
- 기술적 수치만 제시하지 말고 가능한 경우 사용자·운영 관점의 영향을 설명한다.
- Kanto는 담당 기능 전체보다 핵심 기여 1~2개와 결과를 우선한다.
- 기술 스택은 왜 선택했는지 또는 무엇을 해결했는지와 연결한다.
- npm 다운로드, GitHub Star, 방문 수, PR·이슈처럼 외부 검증 지표가 실제로 존재하면 제시한다.
- 없는 외부 지표나 측정하지 않은 개선 수치를 임의로 만들지 않는다.
- 이력서와 포트폴리오에서 같은 성과의 수치와 측정 기준을 동일하게 쓴다.

### 1.2 권태하 매니저 피드백

권태하 매니저의 핵심 지적은 기술적 해결과 협업이 서로 분리되어 보인다는 점입니다.

- 이력서에서 주장한 내용은 포트폴리오에서 직접 확인할 수 있어야 한다.
- 문제가 발생했을 때 팀에 어떻게 공유했는지 보여준다.
- 어떤 기준으로 우선순위를 정했는지 보여준다.
- 팀원의 의견을 어떻게 취합하고 해결안을 결정했는지 설명한다.
- 일정 관리·주간 보고서를 운영했다는 사실만 적지 말고, 실제 문제 해결에 어떻게 사용했는지 연결한다.
- 개인 프로젝트에서도 문제 인지, 원인 정리, 대안 비교, 우선순위 판단 과정을 보여준다.

### 1.3 김기수 멘토 피드백

- 현재 포트폴리오는 문제 발견과 성능 개선 수치를 보여주는 방향이 강점이다.
- 모든 프로젝트가 비슷한 형식으로 반복되므로 프로젝트별 대표 강점을 다르게 보여줘야 한다.
- AI를 사용했다는 사실보다 AI로 해결한 문제와 검증 결과가 먼저 보여야 한다.
- 프로젝트별 GitHub·배포·npm 링크를 제공해 직접 확인할 수 있게 한다.
- 포트폴리오가 다소 산만하게 보일 수 있으므로 정보 우선순위와 페이지별 메시지를 단순화한다.

### 1.4 김성박 강사 피드백

- `프론트엔드에 뿌리를 두고 팀의 구조를 세우는 개발자`라는 정체성을 앞에 세운다.
- 표지 다음 장에서 대표작, 강점, 역할이 한눈에 들어오게 한다.
- 네 프로젝트를 같은 비중으로 늘어놓지 않고 Kanto를 대표작으로 둔다.
- 파이널 1위 결과만 보여주지 말고, 구조·일정·보고 체계를 운영하며 팀이 움직이게 한 역할을 설명한다.
- 트러블슈팅은 대표 사례 2~3개만 깊게 남긴다.
- 장식보다 내용이 먼저 읽히도록 여백과 정보 밀도를 정리한다.

### 1.5 최종프로젝트 평가 피드백

최종프로젝트 평가는 포트폴리오 첨삭이 아니지만 Kanto의 결과와 개인 기여를 구분하는 근거로 사용합니다.

- `총점 96점`, `기술 구현·완성도 40/40`, `코드 품질·최적화 30/30`, `협업·형상 관리 16/20`, `문서화·발표 10/10`은 팀 평가다.
- 평가자가 기술 완성도의 근거로 언급한 채팅, SEO, 다국어, 번역 API fallback, 요청 제한, 예외 처리는 김도혁의 실제 작업과 연결되는 항목이 많다.
- Git Flow와 리뷰 참여는 긍정적이었지만 리뷰가 실제 품질 관문으로 충분히 작동하지 않아 협업에서 감점됐다.
- 따라서 포트폴리오에서 `완벽한 리뷰 체계를 구축했다`고 표현하지 않는다.
- 팀 전체의 테스트·CI·문서 성과를 개인이 모두 수행한 것처럼 표현하지 않는다.

## 2. 포트폴리오 수정 시 공통 요구사항

### 요구사항 1. 표지 다음 장에서 정체성과 대표 근거를 연결한다

표지의 개발자 정체성은 수정된 이력서와 같은 방향이어야 합니다.

> 구조를 고민하고 실측을 토대로 작업하는 프론트엔드 개발자

다음 장에서는 이를 추상적인 성향으로 다시 설명하지 않고 대표 근거로 증명합니다.

- 구조: 실시간 채팅 상태 구조, 운영관리 구조, 서버/UI 상태 분리
- 실측: GET 요청 18회→3회, 렌더링 최대 8.2배, Lighthouse 측정
- 결과: Kanto 팀 평가 96점·5개 팀 중 1위

### 요구사항 2. Kanto를 대표 프로젝트로 명확히 구분한다

- 프로젝트 개요에서 Kanto가 대표작임을 바로 알 수 있어야 한다.
- 팀 결과와 개인 역할을 같은 문장으로 섞지 않고 구분한다.
- 팀 결과 다음에 김도혁이 직접 소유한 채팅·운영 기능·성능 개선 근거를 배치한다.
- Kanto의 기능 전체를 본인 기능처럼 보이게 나열하지 않는다.

### 요구사항 3. 이력서의 결론을 포트폴리오가 과정으로 증명한다

이력서는 결과를 짧게 보여주고 포트폴리오는 다음 질문에 답해야 합니다.

1. 어떤 문제가 있었는가?
2. 어떻게 재현하거나 측정했는가?
3. 원인을 무엇으로 판단했는가?
4. 어떤 대안을 검토했는가?
5. 왜 이 해결 방법을 선택했는가?
6. 어떻게 구현했는가?
7. 무엇으로 결과를 검증했는가?
8. 남은 한계는 무엇인가?

### 요구사항 4. 기술 문제와 협업 과정을 한 흐름으로 연결한다

현재처럼 `문제해결` 페이지와 `협업 방식` 페이지를 완전히 분리하면 기술은 개인 작업, 협업은 행정 작업처럼 보입니다.

권장 흐름:

> 문제 발견 → 팀 공유 → 담당자·우선순위 결정 → 구현 및 리뷰 → 완료 상태 추적 → 결과 확인

주간 보고서와 WBS는 존재 자체보다 다음 상황에서 어떻게 사용했는지를 보여줍니다.

- 외부 멘토 리뷰 1~4차 대응
- 기능 증가로 일정이 흔들렸을 때 성능 감사와 안정화로 범위를 조정한 과정
- 배포 직전 hotfix 규칙을 만들고 신규 기능을 제한한 과정

### 요구사항 5. 대표 트러블슈팅 수를 제한한다

- 한 프로젝트에 문제해결 사례를 계속 추가하지 않는다.
- 포트폴리오 전체에서 개발자 정체성을 가장 잘 증명하는 사례 2~3개를 우선한다.
- 같은 메시지를 주는 사례는 하나만 남기고 나머지는 프로젝트 개요의 짧은 성과로 이동한다.

우선순위가 높은 후보:

1. Kanto 관리자 GET 요청 18회→3회 — 서버/UI 상태 분리와 재현 조건
2. `markdown-block-preview` 최대 8.2배 — 파싱과 DOM 비용을 분리한 실측
3. Kanto 채팅·운영 기능 — 초석 구현 범위와 번역 API 장애 fallback

### 요구사항 6. 프로젝트별 역할을 다르게 만든다

| 프로젝트 | 포트폴리오에서 맡을 역할 |
|---|---|
| Kanto | 팀 프로젝트에서 핵심 기능과 운영 구조를 구축한 대표작 |
| DoHyuk.dev | 병목을 분리 측정하고 npm 패키지로 확장한 개인 기술 프로젝트 |
| ESLint-KR | 학습 문제를 문서와 자동 검증으로 해결한 문서화 프로젝트 |
| Frontie | 멀티 LLM 통합과 렌더링 성능 개선을 짧게 보여주는 실험 프로젝트 |

### 요구사항 7. 수치마다 증명 조건을 붙인다

- `18회→3회`: 탭 5회 왕복과 룰 등록·목록 조회, 브라우저 네트워크 탭
- `최대 8.2배`: 50블록 문서에서 1블록 변경 조건과 비교 대상
- `48 → PC 92 · Mobile 100`: Lighthouse와 측정 화면
- `9가지 사용자 패턴`: 시나리오 구성과 등급 분포 결과
- `96점·1위`: 팀 평가 결과임을 표시하고 평가표 또는 출처를 연결

### 요구사항 8. AI는 방법으로만 남긴다

- `AI 챗봇`처럼 제품 자체가 AI인 경우에는 핵심 기능으로 설명할 수 있다.
- 설계·리뷰·보고서 작성에서 사용한 AI는 문제 해결을 보조한 방법으로만 적는다.
- `AI로 기간 단축`, `AI로 효율 향상`처럼 측정 근거가 없는 효과는 사용하지 않는다.
- KTS·KPPS에서는 AI보다 `9가지 사용자 패턴 시뮬레이션과 등급 분포 검증`을 앞에 둔다.

### 요구사항 9. 근거 링크를 결과 가까이에 둔다

- 프로젝트 제목: 배포 링크
- 프로젝트 상단: GitHub 저장소
- npm 패키지 성과: npm 페이지
- 성능 수치: 측정 화면 또는 상세 기록
- 협업 기여: 실제 보고서·리뷰 할당·hotfix 문서
- Kanto 결과: 최종프로젝트 평가표

링크는 아이콘만 두지 말고 필요한 경우 `GitHub`, `npm`, `평가표`, `측정 자료`처럼 목적을 알 수 있는 텍스트를 병기합니다.

### 요구사항 10. 페이지마다 한 가지 결론만 남긴다

- 한 페이지의 제목만 읽어도 무엇을 증명하는지 알 수 있어야 한다.
- 개요·기능·기술 스택·문제해결을 한 페이지에 모두 같은 크기로 배치하지 않는다.
- 장식 이미지보다 문제·판단·결과를 먼저 읽을 수 있게 한다.
- 긴 기술 스택 표는 핵심 기술과 선택 이유만 남긴다.

## 4. Kanto 개인 기여 표기 원칙

### 개인 기여로 사용할 수 있는 범위

- Supabase Realtime 기반 채팅의 타입·상태 관리·송수신·읽음 처리·도배 방지 기반
- 관리자 운영관리의 공지·금칙어·스팸 구조
- 공지사항 한·영·필 자동 번역과 번역 API 장애 fallback
- 관리자 서버 상태의 TanStack Query 전환과 GET 요청 감소
- KTS·KPPS DB·점수 체계와 사용자 패턴 검증
- Redis 기반 로그인 요청 제한
- 외부 멘토 1~4차 리뷰의 담당자·우선순위 재구성
- hotfix 규칙 문서화

### 개인 단독 성과로 쓰지 않을 범위

- 팀 총점 96점과 1위
- 팀 전체 E2E·API 통합 테스트
- 팀 전체 CI·ESLint 개선
- 27개 문서 전체
- 저장소의 외부 멘토 리뷰 20회 이상 전체
- 다른 팀원이 채팅 기반 위에 확장한 미읽음 카운트·신고·차단 기능
