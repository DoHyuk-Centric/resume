## 현재 소개 텍스트

React·Next.js 기반 프론트엔드 개발자로, 부트캠프 파이널 프로젝트 Kanto에서 실시간 채팅·인증 보안·관리자 시스템을 맡아 전체 5개 팀 중 1위를 기록했습니다.

감이 아닌 실측으로 병목을 좁히고 재발 방지까지 연결합니다. 이미지 전송량을 390MB→64MB(−84%), 관리자 GET 요청을 18회→3회(−83%)로 줄였고, 변경 블록만 렌더링하는 npm 패키지를 개발·배포해 마크다운 미리보기 성능을 최대 8.2배 개선했습니다.

## 이전에 사용했던 개인 소개

### Why?

무엇을 하더라도 `왜?`인지 고민해봅니다.

누군가가 저에게 API 요청 함수 또는 데이터를 요청했을 때 왜 필요한지 함께 고민해주기 위해 노력합니다. 보통 무엇인가를 요청할 때 내가 아는 내용이 있다면, 그 부분에서 명확히 제시해주는 것이 요청자의 입장이라고 생각합니다.

### How?

`성능을 개선했다`, `문제를 해결했다`에서는 늘 `어떠한 결과를 가져왔다`, `얼마나 개선되었다`라는 말이 등장합니다.

개발자에게 얼마나 해결되었는지는 매우 중요하지만 동시에 `어떻게?`, `어떤 과정으로?`를 자주 잊어버리게 됩니다. 저는 결과를 도출하는 과정에서 더 많은 시간을 사용하므로 그 과정을 문서로 남기려고 노력합니다.

### 기준을 먼저 세웁니다

모든 일에는 어떤 기준점이 있어야 한다고 생각합니다. 문서를 정리하더라도 그 문서만의 템플릿이 있어야 하며, 어떤 프로젝트를 하더라도 그 프로젝트만의 구조가 있어야 합니다.

무언가를 고민하거나 접근할 때 기준을 먼저 세우면 더 체계적인 해결책에 도달할 수 있었고, 일회성 해결이 아닌 반복 가능한 체계로 발전시킬 수 있었습니다.

## 이전 소개에서 유지할 핵심 정체성

### 1. 요청의 목적부터 확인한다

- 요청받은 기능을 그대로 구현하기 전에 왜 필요한지 확인한다.
- 요청자가 알고 있는 맥락과 개발자가 알고 있는 기술적 맥락을 함께 맞춘다.
- 단순 구현자가 아니라 더 적합한 해결 방법을 함께 찾는 개발자로 표현할 수 있다.

### 2. 결과뿐 아니라 해결 과정을 남긴다

- 개선 수치만 제시하는 것이 아니라 문제 재현, 원인 분석, 선택 근거, 검증 과정을 중요하게 생각한다.
- 이 과정은 현재 이력서의 `실측으로 병목을 좁힌다`는 문장과 연결된다.
- 과정 문서화는 권태하 매니저가 요구한 포트폴리오 근거와도 연결할 수 있다.

### 3. 기준을 세워 반복 가능한 체계로 만든다

- 작업 전에 성공 조건과 판단 기준을 세운다.
- 한 번의 문제 해결로 끝내지 않고 팀이 다시 사용할 수 있는 문서·규칙·자동화로 발전시킨다.
- 현재 프로젝트의 코드 리뷰 할당 문서, hotfix 규칙, CI·주간 스모크 테스트가 이를 증명할 수 있다.

## 소개 한 줄 후보

### 후보 1 — Why·기준·실측 통합형 (추천)

> 요청의 목적을 묻고, 기준과 실측으로 답을 찾는 React·Next.js 프론트엔드 개발자입니다.

장점:

- 이전 소개의 `Why?`, `How?`, `기준`을 한 문장에 모두 담을 수 있다.
- 현재 이력서의 실측 기반 성과와 연결된다.
- 다른 지원자와 구분되는 개발 방식을 보여준다.

### 후보 2 — 문제 해결 중심형

> 문제를 재현할 기준을 세우고, 실측으로 원인을 좁혀 해결하는 프론트엔드 개발자입니다.

장점:

- 가장 간결하다.
- 이력서의 성능 개선 사례와 직접 연결된다.

아쉬운 점:

- 요청의 목적을 함께 고민한다는 협업 태도가 잘 드러나지 않는다.

### 후보 3 — 문서화·체계 중심형

> 해결 과정을 문서로 남겨 일회성 대응을 반복 가능한 체계로 만드는 프론트엔드 개발자입니다.

장점:

- 문서화와 재발 방지라는 강점이 선명하다.
- 코드 리뷰 문서, hotfix 규칙, CI 자동화 사례와 연결하기 쉽다.

아쉬운 점:

- React·Next.js 직무 정체성과 실측 기반 문제 해결이 첫 문장에 드러나지 않는다.

### 일반 텍스트

원인·선택 근거·검증 결과를 문서로 남겨 일회성 해결을 반복 가능한 체계로 발전시킵니다. Kanto에서 원본 이미지 업로드를 트래픽 급증 원인으로 특정하고 WebP 변환을 적용해 전송량을 84% 줄였으며, 프로젝트는 전체 5개 팀 중 1위를 기록했습니다.

## 추천 수정안의 문장별 역할

1. `요청의 목적을 묻고`  
   이전 소개의 `Why?`를 압축한 표현이다.
2. `기준과 실측으로 답을 찾는`  
   이전 소개의 `How?`와 `기준을 먼저 세웁니다`를 통합한 표현이다.
3. `API나 데이터 요청을 바로 구현하기보다 왜 필요한지 함께 확인하고`  
   권태하 매니저가 요구한 협업 상황의 구체성을 보완한다.
4. `원인·선택 근거·검증 결과를 문서로 남겨`  
   김기수 멘토가 긍정적으로 평가한 개발 스타일을 유지한다.
5. `일회성 해결을 반복 가능한 체계로 발전시킵니다`  
   단순한 문서 작성을 넘어 문서화의 목적을 설명한다.
6. `WebP 변환으로 전송량 84% 절감`  
   추상적인 성향을 실제 기술적 행동과 결과로 증명한다.
7. `전체 5개 팀 중 1위`  
   대표 팀 프로젝트의 결과를 짧게 제시한다.

## 이번 수정안에서 의도적으로 제외한 내용

- 이미지 전송량 84%, GET 요청 83%, npm 패키지 8.2배를 모두 나열하지 않았다.
- 소개에는 대표 성과인 Kanto 이미지 트래픽 84% 절감만 사용했다.
- GET 요청 83% 절감과 npm 패키지 8.2배 개선은 프로젝트 항목에서 확인하도록 역할을 분리했다.
- AI 활용과 개발 기간 단축 표현은 근거 문제와 키워드 반복 때문에 제외했다.
- KTS·KPPS, 실시간 채팅, 관리자 시스템 등 담당 기능 전체를 소개에 다시 나열하지 않았다.

## 강점 재정의

1차 추천 수정안은 Why·기준·실측·문서화를 모두 설명했지만, 읽는 사람이 `그래서 가장 큰 강점이 무엇인가?`를 한 번 더 해석해야 한다는 문제가 있습니다.

따라서 여러 행동을 하나의 핵심 강점으로 묶습니다.

### 핵심 강점

> 요청에서 해결해야 할 문제를 찾고, 성공 기준부터 정의하는 능력

### 핵심 강점을 구성하는 세 가지 행동

| 행동 | 의미 | 실제 근거 |
|---|---|---|
| 목적과 성공 기준 확인 | 요청을 그대로 구현하지 않고 왜 필요한지와 완료 조건을 먼저 확인한다. | API·데이터 요청의 목적 확인, 프로젝트별 구조와 문서 템플릿 수립 |
| 재현과 실측 | 감으로 원인을 추정하지 않고 동일 조건을 만들어 병목을 측정한다. | 이미지 전송량 390MB→64MB, GET 요청 18회→3회, 마크다운 렌더링 최대 8.2배 개선 |
| 문서화와 체계화 | 개인의 일회성 해결을 팀이 반복할 수 있는 기준으로 바꾼다. | 외부 멘토 리뷰 20회 이상 담당자·우선순위별 정리, hotfix 규칙, CI·주간 스모크 테스트 |

### 강점 표현에서 제외할 단어

- `꼼꼼한`, `성실한`, `문제 해결 능력이 좋은`처럼 누구나 사용할 수 있는 형용사는 사용하지 않는다.
- `Why`, `How`를 제목처럼 직접 나열하지 않는다. 실제 행동 문장 안에서 보여준다.
- `체계적`이라는 단어만 단독으로 사용하지 않는다. 어떤 기준과 문서를 만들었는지 근거를 함께 제시한다.
- 기술 스택은 강점 그 자체가 아니므로 React·Next.js는 직무 정체성을 알려주는 수준으로만 사용한다.

## 2차 추천 수정안 — 강점 중심

전체 5개 팀 중 1위를 기록한 Kanto에서 원본 이미지 업로드를 트래픽 급증 원인으로 특정해 전송량을 84% 줄였습니다. 또한 20회 이상의 코드 리뷰를 담당자·우선순위별 문서로 재구성해 팀이 같은 기준으로 개선 사항을 추적하도록 만들었습니다.

|---|---|---|
| 첫인상 | 요청의 목적을 묻는 개발자 | 진짜 문제와 성공 기준부터 정의하는 개발자 |
| 강점 범위 | Why·기준·실측을 병렬로 제시 | 세 행동을 `문제 정의`라는 하나의 강점으로 통합 |
| 기술적 증거 | 이미지 전송량 84% 절감 | 이미지 전송량 84% 절감 |
| 협업 증거 | 문서화에 대한 일반적인 설명 | 코드 리뷰 20회 이상을 담당자·우선순위별로 재구성한 사례 |
| 차별성 | 사고방식이 보이지만 다소 추상적 | 강점과 근거가 바로 연결됨 |

## 2차 수정안의 문장별 역할

1. `요청을 그대로 구현하지 않고, 해결해야 할 문제와 성공 기준부터 정의하는`  
   가장 큰 강점을 한 문장으로 정의한다.
2. `왜 필요한지 확인한 뒤`  
   이전 소개의 Why와 기준 설정 습관을 구체적인 행동으로 바꾼다.
3. `같은 조건에서 문제를 재현하고, 실측으로 원인과 개선 결과를 검증합니다`  
   How를 재현과 측정이라는 검증 가능한 개발 방식으로 표현한다.
4. `원본 이미지 업로드를 트래픽 급증 원인으로 특정해 전송량을 84% 줄였습니다`  
   문제 구조화와 실측이 실제 기술 성과로 이어졌음을 증명한다.
5. `20회 이상의 코드 리뷰를 담당자·우선순위별 문서로 재구성`  
   문서화가 개인 기록이 아니라 팀의 실행 기준을 만드는 행동임을 증명한다.
