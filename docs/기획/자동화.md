# 자동화 및 테스트 기획

> 문서 상태: 초안

## 1. 목표

반복 작업을 줄이는 것뿐 아니라 잘못된 타입, API 계약 불일치, 인쇄 레이아웃 손상, DB 변경 실패와 배포 후 장애를 배포 전에 발견한다.

## 2. 전체 파이프라인

```text
Pull Request
  → 의존성 설치
  → ESLint
  → Type Check
  → Unit/Integration Test
  → Next.js/NestJS Build
  → Playwright E2E
  → Preview 확인
  → 승인 및 main 병합
  → Production 배포
  → Health/Smoke Test
```

검사에 실패한 PR은 `main`에 병합하지 않는다.

## 3. 역할 분리

### Vercel

- `apps/web` Preview 배포
- 운영 브랜치의 Production 배포
- Next.js 빌드
- 배포별 임시 URL

### GitHub Actions

- 모노레포 전체 ESLint
- FE·BE Type Check
- 단위·통합·E2E 테스트
- Next.js와 NestJS 빌드
- OpenAPI 생성 결과 검사
- 단계적으로 NestJS AWS 배포 자동화

### AWS

- NestJS 실행
- PostgreSQL 및 백업
- S3 파일 저장
- 운영 모니터링과 비용 알림

## 4. 코드 품질 자동화

권장 스크립트:

```text
lint       → ESLint
typecheck  → tsc --noEmit
test       → 단위·통합 테스트
build      → 실제 배포 빌드
e2e        → Playwright
verify     → 위 검사를 순서대로 실행
```

Next.js 빌드가 ESLint를 대신한다고 가정하지 않는다. Vercel Build Command에서도 `verify` 또는 필요한 검사를 명시적으로 실행한다.

## 5. FE·BE 타입 계약

```text
NestJS DTO
  → Swagger/OpenAPI 생성
  → openapi.json
  → Next.js API 타입 생성
  → Type Check
```

CI에서는 타입을 다시 생성한 뒤 Git diff가 생기는지 확인한다. 차이가 있으면 생성 타입이 최신이 아니므로 실패시킨다. 프론트에서 백엔드 응답 타입을 별도로 복사해 선언하지 않는다.

## 6. 테스트 계층

| 계층 | 도구 | 대상 |
|---|---|---|
| 단위 테스트 | Vitest 또는 Jest | 순수 함수, UI 로직, Service |
| BE 통합 테스트 | Jest + Supertest | Controller, Guard, DB 경계 |
| E2E | Playwright | 실제 사용자 흐름 |
| 시각 회귀 | Playwright Screenshot | 템플릿과 Print CSS |
| 배포 Smoke | Playwright/API 요청 | 로그인 페이지, Health, 핵심 조회 |

모든 경우를 E2E로 검사하지 않는다. 비즈니스 분기 대부분은 빠른 단위·통합 테스트로 검증하고, 사용자 핵심 흐름만 Playwright에 둔다.

## 7. Playwright 범위

### 핵심 시나리오

1. 회원가입·로그인
2. 프로젝트 콘텐츠 생성
3. 문서 생성 및 콘텐츠 추가
4. 블록 순서 변경과 저장
5. 템플릿 변경
6. 새로고침 후 상태 유지
7. 다른 사용자 문서 접근 차단
8. 인쇄 미리보기와 A4 레이아웃

### 실행 원칙

- 초기 기능 E2E는 Chromium 중심
- 중요한 반응형 화면만 모바일 Chrome·Safari 추가
- CI worker는 안정성을 위해 1개부터 시작
- 첫 재시도에 Trace 수집
- 실패 시 Screenshot과 HTML Report 업로드
- 운영 DB가 아닌 전용 테스트 DB 사용
- 각 테스트는 독립 사용자·데이터를 만들고 정리

공식 참고:

- [Playwright CI](https://playwright.dev/docs/ci)
- [Trace Viewer](https://playwright.dev/docs/trace-viewer-intro)
- [Visual Comparisons](https://playwright.dev/docs/test-snapshots)

## 8. 인쇄 및 PDF 자동 검증

Playwright의 print media 에뮬레이션과 Screenshot 비교를 사용한다.

```ts
await page.emulateMedia({ media: "print" });
await expect(page).toHaveScreenshot("resume-print.png", {
  fullPage: true,
});
```

Chromium의 `page.pdf()`로 파일 생성 여부를 검사할 수 있지만 PDF 생성 성공만으로 레이아웃 품질을 보장하지 않는다. 시각 비교를 함께 사용한다.

시각 테스트는 OS, 브라우저와 폰트에 민감하므로 기준 이미지와 CI 실행 환경을 통일한다. 기준 이미지 갱신은 자동 승인하지 않고 PR에서 변경 내용을 확인한다.

## 9. DB 마이그레이션 자동화

```text
백업 확인
  → 하위 호환 마이그레이션
  → NestJS 배포
  → Health Check
```

- 추가 중심의 안전한 변경만 자동 실행 대상으로 검토한다.
- 컬럼 삭제, 타입 변경과 대량 데이터 변환은 수동 승인한다.
- 애플리케이션과 DB 배포는 이전·이후 버전이 잠시 공존해도 동작하도록 설계한다.
- 실패 시 앱 롤백만으로 해결되는지, DB roll-forward가 필요한지 미리 기록한다.

## 10. NestJS 배포 자동화 단계

```text
1단계: CI에서 검사와 빌드
2단계: 배포 artifact 또는 Docker 이미지 생성
3단계: AWS 저장소 업로드
4단계: Lightsail 새 버전 실행
5단계: Readiness 검사
6단계: 실패 시 직전 버전 복구
```

AWS 인증은 장기 Access Key보다 GitHub Actions OIDC와 제한된 IAM Role을 우선 검토한다.

## 11. 운영 자동화

- 매일 PostgreSQL 백업 후 S3 업로드
- 백업 성공 여부와 파일 크기 확인
- S3 Lifecycle에 따른 오래된 백업 삭제
- 주기적 DB 복원 훈련
- 사용되지 않는 업로드 파일 정리
- 만료된 PDF와 Export 작업 정리
- AWS Budget 및 리소스 알림
- Dependabot 의존성 업데이트 PR
- 인증서 갱신 및 만료 감시

Dependabot PR은 자동 병합하지 않고 전체 CI 통과와 변경 내용을 확인한다.

## 12. 자동화 우선순위

1. ESLint
2. Type Check
3. Next.js·NestJS Build
4. 핵심 단위 테스트
5. Playwright 핵심 흐름 3~5개
6. Vercel Preview/Production
7. PostgreSQL S3 백업
8. AWS 비용·장애 알림
9. NestJS 자동 배포와 롤백
10. DB 마이그레이션 승인 흐름
11. 서버 PDF Worker와 작업 큐

## 13. 예상 문제와 대응

| 문제 | 대응 |
|---|---|
| E2E가 느리고 불안정함 | 핵심 흐름만 유지, CI worker 1, 명시적 locator 사용 |
| Screenshot이 환경마다 다름 | 동일 CI 이미지·폰트·브라우저 버전 사용 |
| Preview가 운영 API를 변경함 | Preview 전용 환경과 계정 사용 |
| 프론트가 API보다 먼저 배포됨 | 하위 호환 API 선배포와 계약 검사 |
| 자동 마이그레이션이 데이터를 손상함 | 파괴적 변경 수동 승인과 사전 백업 |
| CI 비밀키 유출 | OIDC, 최소 권한, 로그 마스킹 |

## 14. 미결정 사항

- GitHub Actions 무료 사용량을 넘을 때의 AWS CI 이전 방식
- Playwright 브라우저 범위
- 테스트 DB 생성·초기화 방식
- NestJS 배포 artifact 형식
- OpenAPI 타입 생성 도구
- 시각 테스트 기준 이미지 승인 절차
