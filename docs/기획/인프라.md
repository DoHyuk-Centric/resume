# 인프라 기획

> 문서 상태: 초안  
> 비용 원칙: 유료 지출은 AWS에만 사용

## 1. 목표

MVP의 월 고정 비용을 낮게 유지하면서 Next.js 프론트엔드, NestJS API, PostgreSQL과 사용자 파일을 배포한다. 초기에는 단순한 구조를 사용하고 사용량과 안정성 요구가 확인된 후 관리형 서비스로 분리한다.

## 2. 초기 구성

```text
GitHub
├─ apps/web → Vercel Hobby
└─ apps/api → AWS Lightsail

AWS Lightsail 2GB
├─ Caddy 또는 Nginx
├─ NestJS
└─ PostgreSQL

AWS S3
├─ 사용자 이미지
├─ PDF
└─ PostgreSQL 백업
```

### 비용 정책

- Vercel과 GitHub는 무료 허용량 안에서만 사용한다.
- 외부 서비스의 무료 한도를 넘으면 유료 전환하지 않고 AWS 대안을 검토한다.
- 도메인, 서버, 저장소, 이메일 등 유료 비용은 AWS에 집중한다.
- AWS Budget과 비용 알림을 서버 생성 전에 설정한다.

## 3. Vercel 사용 범위

Vercel은 Next.js 프론트엔드의 Preview 및 Production 배포에 사용한다.

2026-07-22 확인 기준 Hobby 주요 제한:

- 프로젝트 200개
- 하루 배포 100회
- 동시 빌드 1개
- 빌드당 최대 45분
- 개인·비상업적 용도

참고:

- [Vercel Limits](https://vercel.com/docs/limits)
- [Vercel Hobby Plan](https://vercel.com/docs/plans/hobby)
- [Vercel Terms](https://vercel.com/legal/terms)

제품이 상업 서비스가 되거나 Hobby 조건을 벗어나면 프론트엔드를 AWS Amplify 또는 S3·CloudFront 등 AWS 구성으로 이전한다. 이 이전 가능성을 위해 프론트엔드가 Vercel 전용 저장 기능에 강하게 결합되지 않도록 한다.

## 4. Lightsail 운영

2GB 인스턴스를 초기 기준으로 삼는다. 1GB는 NestJS, PostgreSQL과 운영체제를 함께 실행하기에 여유가 적다.

### 네트워크

- 외부 공개: 80, 443, 제한된 관리 포트
- PostgreSQL 5432는 외부 공개 금지
- NestJS 포트는 리버스 프록시 뒤에서만 접근
- SSH는 가능한 한 허용 IP 제한 및 키 인증
- HTTPS는 Caddy 자동 인증서 또는 명시적 인증서 정책 사용

### 배포 원칙

- 서버에서 소스 빌드를 반복하지 않고 CI에서 검증된 결과물을 배포한다.
- 컨테이너 또는 artifact에 배포 버전을 표시한다.
- Health Check 성공 후 새 버전을 활성화한다.
- 직전 정상 버전으로 되돌릴 수 있어야 한다.

## 5. 프론트엔드와 API 통신

운영 API는 `api.example.com`, 웹은 `www.example.com` 같은 명시적 주소를 사용한다.

### 예상 문제

- Vercel Preview URL이 매번 바뀌어 CORS 허용 목록 관리가 어려움
- 쿠키 인증에서 domain, SameSite, Secure 설정 오류
- 프론트 배포와 API 배포 순서가 어긋나 계약 불일치 발생

### 대응

- 운영 Origin은 정확한 주소만 허용
- Preview용 별도 API 및 제한된 Origin 정책 검토
- OpenAPI 호환성 검사
- API 변경은 하위 호환 배포 후 프론트 배포
- 광범위한 `*.vercel.app` CORS 허용 금지

## 6. S3 정책

- 공개 버킷 사용 금지
- 사용자 파일은 기본 private
- 다운로드와 업로드는 짧은 만료의 Presigned URL 사용
- 사용자별 key prefix
- 파일 크기와 MIME 제한
- 백업과 사용자 파일의 prefix 또는 bucket 분리
- Lifecycle로 임시 파일과 오래된 백업 삭제
- 필요한 경우 버전 관리와 암호화 활성화

## 7. 백업 및 장애 대응

```text
매일 Cron
  → pg_dump
  → 압축
  → S3 업로드
  → 체크섬/크기 확인
  → 실패 알림
```

단일 Lightsail 서버 장애 시 API와 DB가 함께 중단되는 위험을 수용하는 대신 다음을 준비한다.

- 새 인스턴스 생성 절차
- 애플리케이션 환경변수 복원 절차
- S3 백업에서 PostgreSQL 복원 절차
- DNS 전환 절차
- 복원 테스트 기록

## 8. 모니터링과 비용 알림

초기 필수 항목:

- CPU 및 메모리
- 디스크 사용률
- `/health/live`, `/health/ready`
- HTTP 5xx
- PostgreSQL 연결 실패
- 백업 실패
- S3 업로드 실패
- 인증서 만료
- 월 AWS 예상 비용

로그에 개인정보, 토큰, 쿠키와 Presigned URL을 기록하지 않는다. 로그 보존 기간을 제한해 디스크 고갈을 방지한다.

## 9. 성장 단계

```text
1단계: Lightsail에 NestJS + PostgreSQL
2단계: 파일과 백업을 S3로 완전 분리
3단계: PostgreSQL을 Lightsail Managed DB 또는 RDS로 이전
4단계: NestJS 서버와 PDF Worker 분리
5단계: 필요 시 로드 밸런서와 다중 인스턴스 검토
6단계: 상업화 시 Next.js를 AWS로 이전
```

## 10. 피해야 할 초기 구성

- EKS
- 불필요한 마이크로서비스
- ECS Fargate와 복잡한 네트워크 구성
- NAT Gateway가 필요한 구조
- 초기 RDS Multi-AZ
- API 요청 안에서 Chromium 동기 실행

이 서비스들은 요구가 확인된 뒤 비용과 운영 이점을 비교해 도입한다.

## 11. 대안과 트레이드오프

| 대안 | 장점 | 단점 | 판단 |
|---|---|---|---|
| Lightsail 단일 서버 | 낮고 예측 가능한 비용 | DB 운영과 단일 장애점 | MVP 채택 |
| Lightsail Managed DB | 자동 백업과 운영 부담 감소 | 월 고정 비용 증가 | 사용자 증가 후 검토 |
| Lambda/API Gateway | 유휴 비용 감소 | PostgreSQL 연결·배포 복잡도 | 초기 제외 |
| AWS Amplify | Next 배포 통합 | 비용·지원 범위 검토 필요 | Vercel 이전 시 검토 |
| S3/CloudFront 정적 배포 | 저렴하고 안정적 | SSR 기능 제약 | 정적화 가능 범위에 따라 검토 |

## 12. 미결정 사항
