프로필 페이지 · 칸토 망고 점수

당근온도처럼 신뢰가 핵심인 서비스엔 신뢰도를 시각적으로 보여줄 지표가 필요하다고 판단해 KTS(신뢰도)·KPPS(인기도) 점수 시스템을 설계했습니다.

  • KTS 공식 KTS = clamp(36 + Review + Transaction + Activity + Trend − Penalty, 0, 100)

    Review 리뷰 평점 · Transaction 거래 완료 · Activity 활동 · Trend 등급 추이 · Penalty 신고·제재

  • KPPS 공식 KPPS = clamp(Engagement + LikeRate + KTSBonus + Quality + Recency − Report, 0, 100)

    Engagement 좋아요·조회수 · LikeRate 좋아요 전환율 ·
    KTSBonus 신뢰등급 · Quality 이미지·정보 완성도 ·
    Recency 최신성 · Report 신고

  • 9가지 유저 시나리오로 시뮬레이션해 등급 분포(A 7%·
    B 22%·C 45%·D 22%·E 4%)를 사전 검증한 뒤 기준 확정
  • 작성자가 E등급이면 위험수준 유저라고 판단해 순위·점수와 무관하게 배지 제외
  • 점수는 매일 일정 시간 pg_cron으로 자동 재계산

채팅 · 관리자 채팅 로그

유저 간의 소통을 위해 Supabase Realtime 기반 1:1 채팅을 전체 구현하고, 운영적 측면에서 생각해 법적 분쟁·사용자 문의에 대응할 수 있는 관리자 도구를 구축했습니다.

사용자

  • Realtime 메시지 송수신·읽음 처리에 읽지 않은 메시지 구현
  • 언마운트 시 리셋 + 낙관적 업데이트 적용
  • N초 내 N회 이상 전송 시 도배 방지 쿨다운 적용(관리자 운영관리에서 수정 기능 연동)

  • 관리자가 신고된 채팅방의 대화 내역을 페이지네이션으로 조회(최대 20개씩 로드)

문제해결

Supabase 트래픽 한도 초과 대응

기획 단계에서 무료 플랜의 트래픽·토큰 한도를 미리 계산해 소진 시나리오와 대응 전략을 세워뒀지만, 실제로는 예상 밖의 지점에서 문제가 터졌습니다.

7/1 Storage Egress 390MB(전체 88.7%) 급증 → WebP 전환 후 재발 없음

  • 이미지를 WebP로 사전 전환해두지 않은 상태에서, 시연 준비 중 봇 계정과 목업 이미지를 대량 등록하다 Supabase 트래픽 한도 초과가 발생했습니다.
  • 사전에 세워둔 대응 전략은 있었지만 트래픽에서 문제가 터질 것이라곤 생각하지 못했습니다.
    하지만 과도한 트래픽은 최근 추가한 봇과 게시글이 원인일 것으로 추정해 이미지 용량으로 특정했습니다.
  • DB 양이 많아 부계정 이전 대신 유료 플랜 전환으로 즉시 정상화하고, 업로드 단계 WebP 변환 로직을 추가해 동일 조건으로 이미지를 올려도 390MB → 64MB(약 84% 감소)로 트래픽이 안정적임을 확인해 재발 방지까지 검증했습니다.

내 프로필 페이지 - 서버/클라이언트 컴포넌트 분리

프로필 페이지를 처음 구현할 때는 로그인·회원가입 페이지가 아직 구현되기 전이라, 빠른 개발을 위해 목업 데이터를 쓰는 클라이언트 컴포넌트로 만들었습니다. 이후 Supabase API로 실제 데이터를 연결하고 소셜 로그인 "연결하기/연결됨" 버튼과 관심 카테고리를 구현하는 과정에서, 깜빡이는 CLS(레이아웃 시프트) 현상이 생겼습니다.

  • 원인은 각 섹션이 클라이언트 훅에서 자체적으로 데이터를 불러오던 구조였기 때문이었습니다. 페이지가 먼저 빈 상태로 그려지고, 그 다음 브라우저에서 데이터를 요청해오니 버튼·카테고리가 늦게 나타난 것이었습니다.
  • 팀 컨벤션에 따라 페이지 전체를 서버 컴포넌트로 두고, 필요한 데이터를 서버에서 미리 불러와 완성된 상태로 클라이언트에 내려주는 구조로 전환했습니다. 클라이언트 훅은 자체 fetch 로직을 걷어내고, 서버가 준 초기값만 받아쓰도록 단순화했습니다.
  • 이후 페이지가 복잡해지면서(리뷰·모임·활동 통계 등) 늘어난 기능들도 같은 원칙을 유지해, 데이터 조회는 서버 컴포넌트에 모으고 인터랙션만 클라이언트 컴포넌트로 넘기는 구조를 끝까지 지켰습니다.

관리자 콘텐츠 중복 GET 제거 - TanStack Query 캐싱

금칙어·스팸 탭을 전환할 때 컴포넌트가 언마운트되며 useEffect가 다시 실행돼, 이미 조회한 서버 데이터를 반복 요청하고 있었습니다.

  • 서버 조회값을 useState에 두면 탭 언마운트와 함께 사라져, 재진입할 때마다 useEffect가 같은 GET을 반복했습니다. 조회 데이터는 컴포넌트 수명과 분리해 TanStack Query가 관리하고, draft·editingId처럼 화면에만 필요한 상태만 useState에 남겼습니다.
  • 설정·템플릿 수정 결과는 캐시에 즉시 반영해 추가 GET을 막고, 금칙어 CRUD 후에는 해당 목록 캐시만 무효화해 최신 데이터를 다시 조회했습니다.
  • 탭 5회 왕복 + 룰 등록/목록 2회 왕복을 동일하게 재현해 GET 요청이 18회 → 3회(약 83.3% 감소)로 줄어든 것을 네트워크 탭에서 확인했습니다.

로그인 무차별 대입 공격 방지 - Redis(Upstash)

로그인 API에 시도 횟수 제한이 없어 무차별 대입 공격에 취약하다는 문제를 코드 리뷰 중 발견했습니다.

  • 서버 인메모리 카운터로 막으려 했지만, 서버리스 환경은 인스턴스 간 상태가 공유되지 않아 단순 카운터로는 우회가 가능하다는 걸 확인했습니다.
  • Upstash Redis에 IP별 로그인 실패 횟수를 기록하도록 설계해, 인스턴스가 몇 개든 같은 카운터를 공유하도록 만들었습니다.

또한, 글이 길어질수록 재렌더링하는 영역이 많아 성능이 떨어질 것으로 판단했습니다.

원인 실측

  • 전체 문서 재파싱 0.98ms vs 블록 1개만 파싱 0.005ms → 파싱은 병목이 아님
  • 전체 innerHTML 반영 13.45ms vs 블록 1개만 반영 0.18ms → DOM 트리 재구성이 병목
  • naive 방식(매번 전체 재파싱 + innerHTML 통째 교체)은 700블록부터 프레임 예산(16.6ms)을 초과

해결

  • 빈 줄 기준으로 문서를 블록 단위로 나누고, 이전 블록과 비교해 바뀐 블록만 DOM에 반영, 구조가 바뀌면 전체 재구성으로 폴백
  • 마땅한 라이브러리가 없어 별도 npm 패키지로 직접 개발·배포해 이 프로젝트 글쓰기 에디터에 적용
  • 문서 길이와 무관하게 편집당 0.03~0.07ms(naive 대비 최대 8.2배 개선) 유지

이미지 지연 업로드 패턴

처음엔 이미지를 선택하는 즉시 Storage에 업로드했는데, 임시저장 없이 중간에 나가버리면 쓰이지 않는 이미지가 Storage에 그대로 쌓이는 문제가 있었습니다.

  • 발행 시점에만 실제 업로드하도록 바꿨는데, 그 전까지 미리보기는 어떻게 보여줄지가 새로운 문제였습니다.
  • URL.createObjectURL()로 만든 blob: 임시 주소로 해결했습니다 - 파일을 선택하면 브라우저가 그 파일을 가리키는 로컬 주소를 즉석에서 만들어 미리보기에 쓰고, 실제 파일은 별도 Map에 그 주소와 함께 잠깐 담아뒀습니다.
  • 발행 버튼을 누른 시점에만 이 주소들을 찾아 실제로 업로드하고, 마크다운 속 주소를 진짜 업로드된 주소로 바꿔치기해 불필요한 업로드와 고아 이미지 발생을 줄였습니다.
