> 기준 파일: `portfolio.html`, `portfolio.pdf`

> 현재 분량: 15페이지  
> 상태: 수정 전 현재 구조 및 3차 수정 방향 기록

## 1. 수정 목표

포트폴리오는 이력서와 같은 문장을 반복하는 문서가 아니라, 이력서의 결론이 사실임을 과정과 자료로 증명하는 문서로 수정합니다.

### 이력서가 제시하는 결론

- 구조를 고민하고 실측을 토대로 작업한다.
- 마크다운 렌더링 npm 패키지를 개발·배포했다.
- 팀 프로젝트에서 실시간 채팅과 운영 기능을 구축했다.
- Kanto가 팀 평가 96점으로 5개 팀 중 1위를 기록하는 데 기여했다.
- GET 요청을 18회에서 3회로 줄였다.
- 마크다운 미리보기 성능을 최대 8.2배 높였다.
- 9가지 사용자 패턴으로 점수 공식의 등급 분포를 검증했다.

### 포트폴리오가 답해야 하는 질문

1. 무엇을 직접 설계·구현했는가?
2. 왜 그 구조를 선택했는가?
3. 무엇을 측정해 문제를 판단했는가?
4. 팀에서 문제가 발생했을 때 어떻게 공유하고 결정했는가?
5. 결과를 어떤 자료로 검증할 수 있는가?

## 3. 현재 포트폴리오의 강점

### 유지할 강점

- 대부분의 문제해결 사례가 문제·원인·선택·결과 흐름을 갖고 있다.
- Kanto GET 요청 18회→3회는 측정 시나리오와 네트워크 탭 검증이 명확하다.
- DoHyuk.dev는 파싱과 DOM 반영 비용을 분리 측정해 병목을 찾은 과정이 구체적이다.
- KTS·KPPS는 공식, 시나리오, 등급 분포 결과가 모두 제시되어 있다.
- Frontie는 Lighthouse 측정 화면과 적용 기술이 연결되어 있다.
- 각 프로젝트에 배포·GitHub·npm 링크가 존재한다.

### 우선 해결할 문제

1. 이력서에서 대표 기여로 올린 채팅·운영 기능·공지 fallback 근거가 분산되거나 빠져 있다.
2. Kanto 팀 결과와 개인 기여의 경계가 선명하지 않다.
3. 외부 멘토 리뷰 20회 이상 전체를 직접 재구성한 것처럼 읽히는 문장이 있다.
4. 기술 문제해결과 협업 방식이 서로 다른 페이지에서 별개 활동처럼 보인다.
5. 네 프로젝트가 모두 `개요 → 기능 → 기술 스택 → 경험`과 비슷한 형식을 반복한다.
6. 기술 스택과 기능 목록이 길어 페이지의 대표 결론이 늦게 나온다.
7. 전체 15페이지 중 보조 트러블슈팅 비중이 커 대표 강점이 분산된다.

## 6. 페이지별 수정 계획

### 1페이지 — 표지

현재:

> 실측으로 원인을 찾는 개발자

수정 방향:

> 구조를 고민하고 실측으로 검증하는 프론트엔드 개발자

- 이력서의 정체성과 표현을 맞춘다.
- `답이 없는 문제는 없다`처럼 일반적인 문구는 축소한다.
- 표지는 한 문장만 기억되게 한다.

### 2페이지 — About Me를 한 장 요약으로 재구성

현재의 교육·기술·강점 나열 대신 다음 순서를 권장합니다.

1. 대표작 Kanto — 팀 평가 96점·5개 팀 중 1위
2. 본인 역할 — 실시간 채팅 초석, 운영관리 구조, 서버 상태 개선
3. 대표 수치 — 18회→3회, 8.2배, 9가지 사용자 패턴
4. 확인 링크 — GitHub, 배포, npm, 평가표

필수 수정:

- `외부 멘토 리뷰 20회 이상을 재구성` → `외부 멘토 1~4차 리뷰를 담당자·우선순위별로 재구성`
- WebP 84%는 대표 강점에서 제외하고 Kanto 보조 성과로 낮춘다.

### 3페이지 — 프로젝트 개요

각 카드의 대표 성과를 수정된 이력서와 맞춥니다.

| 프로젝트 | 현재 대표 성과 | 변경 방향 |
|---|---|---|
| Kanto | WebP 전송량 84% 절감 | 팀 96점·1위 + 채팅·운영 구조 |
| DoHyuk.dev | npm 패키지 8.2배 | 유지, 50블록 조건 추가 |
| ESLint-KR | 가이드 10페이지 | 10페이지 + 7개 경로 자동 검증 |
| Frontie | Lighthouse 48→PC 92·Mobile 100 | 유지, Vercel AI SDK 통합 맥락 추가 |

### 4페이지 — Kanto 개요

- 서비스 설명을 한 문단에서 한두 문장으로 압축한다.
- `팀 결과`와 `김도혁의 역할`을 별도 카드로 구분한다.
- 팀 결과: 총점 96점·5개 팀 중 1위
- 개인 역할: 채팅 초석, 운영관리, TanStack Query, KTS·KPPS, 리뷰 1~4차 대응
- 프로젝트 전체 기능은 `팀 구현 범위`라고 명시한다.
- 기술 스택 표는 핵심 기술과 사용 이유 중심으로 축약한다.

### 5페이지 — Kanto 채팅·운영 구조

채팅과 공지사항을 `운영 가능한 서비스 구조`라는 하나의 결론으로 묶습니다.

#### 채팅

- 타입·Zustand 상태 구조
- Supabase Realtime 송수신
- 읽음 처리·낙관적 업데이트·도배 방지
- 팀원이 이후 추가한 미읽음 카운트·신고·차단은 확장 범위로 별도 표시

#### 운영관리

- 공지·금칙어·스팸 관리 구조
- 공지 등록 시 한·영·필 자동 번역
- 번역 API 장애 시에도 원문을 저장하는 fallback
- 운영자가 도배 방지 정책을 변경할 수 있도록 연결

### 6페이지 — Kanto 실측·설계

대표 사례 두 개만 남깁니다.

1. 관리자 GET 요청 18회→3회
   - 탭 5회 왕복과 룰 등록·목록 조회
   - useState/useEffect 서버 상태 문제
   - TanStack Query 캐시와 무효화 기준
   - 네트워크 탭 검증
2. KTS·KPPS
   - 점수 공식의 목적
   - 9가지 사용자 패턴
   - 등급 분포 사전 검증

WebP·프로필 서버 컴포넌트·Redis는 이 페이지의 짧은 `기타 개선`로 이동하거나 포트폴리오에서 제외합니다.

### 7페이지 — Kanto 협업 문제해결

기존 WBS와 주간 보고서를 나열하지 않고 실제 사건 흐름으로 재구성합니다.

> 외부 멘토 리뷰 발생 → 1~4차 항목을 담당자·우선순위별 재구성 → 본인 항목 수정 → 완료 상태 추적 → 배포 직전 hotfix 규칙으로 신규 기능 제한 → 최종 평가에서 전날 지적 사항까지 마무리

주의:

- 저장소에 리뷰 문서가 20회 이상 있다는 사실과 본인이 20회 전체를 정리했다는 주장을 분리한다.
- 협업 점수 16/20과 리뷰 품질 관문 부족도 한계로 짧게 인정한다.
- AI 보고서 작성 프롬프트 설명은 핵심 흐름에서 제외하거나 보조 자료로 이동한다.

### 8페이지 — DoHyuk.dev

- 프로젝트 개요는 2~3줄로 압축한다.
- `markdown-block-preview`를 페이지 중심으로 둔다.
- 전체 파싱과 DOM 반영 비용을 분리한 측정 결과를 보여준다.
- 50블록·1블록 변경 기준 최대 8.2배를 이력서와 동일하게 표시한다.
- 이미지 지연 업로드·인증 일원화·저장 유실은 보조 성과 목록으로 압축한다.

### 9페이지 — ESLint-KR

- 긴 시작 동기는 한 문단으로 줄인다.
- ESLint v9 Flat Config 기준 가이드 10페이지를 대표 산출물로 제시한다.
- GitHub Pages 딥링크 404의 원인과 리다이렉트·경로 복원 방식을 짧게 보여준다.
- 쿼리·해시를 포함한 7개 경로와 CI·주간 스모크 테스트를 검증 결과로 강조한다.
- Star·방문 수가 없다면 비워두고 만들지 않는다.

### 10페이지 — Frontie

- 개요와 문제해결을 한 페이지로 합친다.
- Vercel AI SDK로 세 LLM의 스트리밍 응답과 모델 전환을 통합한 구조를 한 그림으로 보여준다.
- Lighthouse 48 → PC 92 · Mobile 100과 측정 화면을 대표 결과로 둔다.
- Zustand 설정 설명과 memo 설명은 성능 결과를 뒷받침하는 수준으로 압축한다.
- `AI를 활용한 프로젝트`보다 `멀티 프로바이더 통합과 렌더링 최적화`가 먼저 보이게 한다.

### 11페이지 — 끝

- 현재 디자인을 유지할 수 있다.
