# 이력서 프로젝트 수정

> 기준 파일: `resume.html`  
> 작성일: 2026-07-20  
> 상태: 수정 전 현재 프로젝트 섹션 기록

## 수정 대상

이 문서는 `resume.html` 2페이지의 `프로젝트` 섹션만 다룬다. 소개 섹션에서 제시한 강점과 모순되지 않도록 확인하되, 프로젝트 전체를 소개 문구에 억지로 맞추기보다 각 프로젝트의 문제·행동·결과가 짧게 드러나도록 수정 과정을 기록한다.

현재 프로젝트는 다음 네 개다.

1. Kanto — 팀 프로젝트
2. Frontie — 개인 프로젝트
3. ESLint-KR — 개인 프로젝트
4. 개인 기술 블로그(DoHyuk.dev) — 개인 프로젝트

## 현재 프로젝트 텍스트

### 1. Kanto

> 기간: 2026.05 - 2026.07  
> 구분: 팀(4인)

- 필리핀 한인 대상 중고거래·구인·부동산 통합 플랫폼 — 실시간 1:1 채팅, Redis 로그인 보안, 관리자 시스템 담당
- 원본 이미지 업로드를 트래픽 급증 원인으로 진단 → 업로드 전 WebP 변환을 적용해 동일 조건 전송량 **390MB→64MB(−84%)**
- useState·useEffect 기반 서버 상태의 중복 요청을 재현 → TanStack Query로 서버/UI 상태를 분리해 GET 요청 **18회→3회(−83%)**
- 외부 멘토의 20회 이상 코드 리뷰를 담당자·우선순위별 문서로 재구성하고, 본인 담당 개선 항목과 팀 진행 상태를 추적
- Next.js · Supabase · TanStack Query · Upstash · GitHub

### 2. Frontie

> 기간: 2026.05 (약 2주)  
> 구분: 개인

- Groq·Gemini·Cerebras를 한 인터페이스에서 전환하는 프론트엔드 학습 챗봇
- 하이라이터 교체·마크다운 렌더러 지연 로딩·memo 적용으로 Lighthouse Performance **48→PC 92·Mobile 100**
- Next.js · Vercel AI SDK · Zustand · GitHub

### 3. ESLint-KR

> 기간: 2026.03 - 2026.04  
> 구분: 개인

- v8·v9 정보가 뒤섞인 학습 문제를 해결하기 위해 v9 Flat Config 기준 한국어 실전 가이드 **10페이지** 제작·배포
- GitHub Pages의 SPA 딥링크 404를 해결하고, 쿼리·해시를 포함한 7개 경로를 CI와 주간 스모크 테스트로 자동 검증
- React · TypeScript · GitHub Actions · GitHub

### 4. 개인 기술 블로그(DoHyuk.dev)

> 기간: 2026.01 - 2026.03  
> 구분: 개인

- 프레임워크 기본기와 번들 구성을 직접 다루기 위해 바닐라 JavaScript·Vite MPA 구조로 구현

## 다음 수정에서 확인할 쟁점

1. Kanto에서 가장 큰 기여인 실시간 1:1 채팅과 공지사항·운영 기능이 현재 성과 문장보다 약하게 보이는 문제
2. Kanto의 1위 결과를 프로젝트 항목에도 넣을지, 교육 섹션의 중복을 피하기 위해 한쪽에만 둘지
3. 소개에 제시된 신뢰도·인기 게시물 점수 공식 검증을 어느 프로젝트의 성과로 연결할지
4. WebP 변환처럼 기본적인 최적화보다 문제 진단과 검증 과정이 더 잘 드러나는 대표 사례가 있는지
5. 각 프로젝트의 설명이 `무엇을 만들었는지 → 어떤 문제를 해결했는지 → 결과가 무엇인지` 순서로 읽히는지
6. Kanto에 성과가 집중되어 5개 문장으로 길고, 나머지 프로젝트는 2~3개 문장인 현재 정보 밀도가 적절한지

### 적용한 공통 요구사항

1. 서비스 설명 뒤에 본인 기여가 바로 나오도록 순서를 조정했다.
2. Kanto의 팀 결과와 김도혁의 직접 구현 범위를 별도 문장으로 분리했다.
3. 기능 이름을 길게 나열하기보다 대표 기능의 소유 범위와 예외 처리를 제시했다.
4. `20회 이상 리뷰 전체 재구성`처럼 실제 범위보다 커질 수 있는 표현을 `외부 멘토 1~4차 리뷰`로 바로잡았다.
5. 기술 스택은 핵심 기술만 남기고, 본문에서는 기술이 해결한 문제와 결과를 설명했다.
6. 프로젝트마다 채팅·운영 안정성·성능·배포 검증·패키지 설계처럼 서로 다른 대표 강점이 보이도록 했다.

## 소개와의 연결 확인

| 소개 내용 | 개선된 프로젝트 근거 |

| 구조를 고민한다 | 채팅 상태 구조, 운영관리 구조, 서버/UI 상태 분리, 변경 블록 렌더링 |
| 실측을 토대로 작업한다 | GET 18회→3회, Lighthouse 48 → PC 92 · Mobile 100, 50블록 기준 8.2배 |
| 마크다운 npm 패키지를 배포했다 | DoHyuk.dev의 패키지 개발·배포 문장과 npm 링크 |
| 채팅 시스템과 운영 기능을 개발했다 | Kanto 채팅 구현 범위와 공지·금칙어·스팸 운영 구조 |
| 파이널 프로젝트 1위에 기여했다 | Kanto의 팀 평가 96점과 5개 팀 중 1위 결과 뒤에 직접 기여를 배치 |

## 이번 반영에서 제외한 내용

- WebP 변환과 전송량 84% 감소는 사실이지만 Kanto의 대표 기여에서 제외했다. 포트폴리오의 성능 개선 사례로는 유지할 수 있다.
- Kanto에서 구현한 모든 관리자·SEO·인증 기능을 이력서에 나열하지 않았다. 채팅과 운영관리, 서버 상태 개선을 대표 사례로 선택했다.
- 팀 전체의 E2E·API 통합 테스트, CI, ESLint 개선은 개인 성과로 사용하지 않았다.
- KTS·KPPS의 9가지 사용자 패턴 검증은 소개와 포트폴리오에 이미 있어 프로젝트 본문의 정보 과밀을 피하기 위해 반복하지 않았다.
