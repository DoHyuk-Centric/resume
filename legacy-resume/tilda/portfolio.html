04. DoHyuk.dev

구현과 문제 해결

변경 블록만 렌더링하는 미리보기

원인

글을 입력할 때마다 우측 미리보기 전체가 다시 렌더링되어 화면이 깜빡이고 작성 흐름을 방해했습니다.

해결

  • 문서를 블록으로 나눠 이전 결과와 비교하고 변경된 블록만 DOM에 반영
  • 구조 변경 시 전체 재구성으로 폴백하는 로직을 패키지로 분리·배포
  • 50블록 기준 0.03~0.07ms, naive 대비 최대 8.2배 개선

병목 측정

  • 파싱보다 전체 innerHTML 교체에 따른 DOM 트리 재구성이 병목
  • 전체 DOM 반영 13.45ms vs 변경 블록 반영 0.18ms

발행 시점 이미지 지연 업로드

문제

이미지를 첨부하는 즉시 Storage에 업로드하면, 글을 발행하지 않고 이탈했을 때 사용되지 않는 이미지가 남았습니다.

해결

Blob URL로 로컬 미리보기를 제공하고, 발행 시점에만 이미지를 Storage에 업로드한 뒤 마크다운의 임시 URL을 실제 URL로 치환했습니다.

업로드 흐름

  1. Blob URL
    미리보기
  2. →
  3. 파일·URL
    Map 보관
  4. →
  5. 발행 시 업로드
    URL 치환
  • URL.createObjectURL()로 업로드 전 로컬 미리보기 제공
  • 발행 시에만 Supabase Storage에 업로드해 불필요한 저장과 불필요 이미지 발생 감소

Frontie

멀티 LLM 기반 프론트엔드 학습 AI 챗봇

개요

  • 부트캠프 팀 프로젝트(Kanto)와 병행한 개인 미니 프로젝트로, 이슈 단위로 브랜치를 나누고 PR로 병합하는 협업 워크플로우를 1인 개발에도 동일하게 적용했습니다.
  • Groq·Gemini·Cerebras 3개 LLM 프로바이더를 하나의 채팅 인터페이스에서 실시간으로 전환하며 쓸 수 있는 프론트엔드 학습용 AI 챗봇입니다.

핵심 기능

  • 멀티 LLM 실시간 전환 - Groq·Gemini·Cerebras 3개 프로바이더를 설정 모달에서 즉시 전환하며 스트리밍 응답 수신
  • 비전 지원 이미지 첨부 - 비전 모델(Groq·Gemini)에만 이미지를 전달하고, 미지원 모델 선택 시 첨부 버튼 자동 비활성화
  • 마크다운·코드 렌더링 - react-markdown·shiki 기반 구문 강조로 코드 답변 가독성 확보
  • 대화 설정 커스터마이즈 - 모델·창의성(temperature)· 언어를 즉시 전환
  • 세션 유지 - Zustand(persist)로 새로고침 후에도 대화 상태 유지

경험 및 문제해결

설정 상태 관리 - Zustand(persist)

설정 모달에서 고른 모델·창의성·언어가 새로고침하면 날아가지 않도록, Zustand(persist)로 저장하고 그 값을 그대로 API 요청까지 이어지도록 설계했습니다.

  • 사용자가 고른 설정값을 브라우저에 자동으로 저장해둬서, 페이지를 새로고침해도 마지막에 선택한 값이 그대로 남아있도록 만들었습니다.
  • 메시지를 보낼 때마다 저장해둔 설정값을 함께 실어 서버로 전달합니다.
  • 서버는 전달받은 값을 보고 Groq·Gemini·Cerebras 중 어떤 AI 모델을 쓸지 그때그때 정합니다.

PC 92점

Mobile 100점

Lighthouse 성능 점수 48점 → PC 92점 · Mobile 100점

기능 구현을 어느 정도 마친 뒤 측정한 Lighthouse 점수가 48점에 그쳤습니다.

개선 방안

  • 코드 하이라이팅을 shiki로 교체
  • ReactMarkdown 등을 지연 로딩으로 전환
  • react-syntax-highlighter가 모든 언어 문법을 번들에 통째로 담고 있었습니다. shiki로 교체해 쓰는 언어만 동적으로 불러오고, 하이라이팅도 서버에서 미리 끝내 보내 초기 JS 용량을 줄였습니다.
  • ReactMarkdown을 메시지를 주고받기도 전에 무조건 불러오고 있었습니다. 실제로 필요한 시점에만 불러오도록 지연 로딩으로 바꾸고, 상호작용이 없는 화면은 서버에서만 처리하도록 분리해 첫 화면이 뜨는 속도를 끌어올렸습니다.

메시지 리스트 리렌더링 최적화 - memo

채팅이 길어질수록 새 메시지 하나가 추가될 때마다 이전 메시지까지 화면 전체가 다시 그려지는 문제를 발견했습니다.

  • 메시지가 쌓일수록 새 메시지 하나가 추가될 때마다 이전 메시지까지 전부 다시 그려지고 있었습니다
  • 원인은 리액트의 기본 동작 방식을 고려하지 못한 제 실수였습니다.
    상태가 하나 바뀌면 화면에 그려진 자식 컴포넌트를 전부 다시 그린다는 것을 알게 되었습니다.
  • MessageItem을 별도 컴포넌트로 분리하고 memo를 적용했습니다. 새 메시지가 추가돼도 기존 메시지들은 자신의 props가 그대로면 리렌더링을 건너뛰고, 새로 추가된 메시지만 실제로 다시 그려집니다. 이를 토대로 대화가 길어져도 체감 성능이 개선되었습니다.
