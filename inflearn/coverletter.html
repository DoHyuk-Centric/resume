1. 지원동기

인프랩이 말하는 "적절한 시기에 적합한 도구로 고객의 문제를 해결한다"는 미션과, 완벽하지 않은 전략도 일단 실행하며 수정해나간다는 "실행"의 가치가 제가 실제 프로젝트에서 판단해온 방식과 같아 지원했습니다. Kanto 프로젝트에서 업종 소분류 데이터를 활용한 비즈니스 페이지를 만들기 시작했지만, 개발이 진행될수록 완성도와 우선순위를 다시 따져봤을 때 지금 이 기능을 배포하는 게 맞는지 의문이 들었습니다. "이것이 정말 지금 풀어야 할 문제인가"를 스스로에게 다시 물었고, 결국 배포 전에 해당 기능을 직접 되돌렸습니다. 완벽하게 짠 코드보다 지금 필요한 게 무엇인지 판단하는 게 먼저라는 것을 이 경험으로 배웠습니다.

직무 측면에서도 React·Next.js·TypeScript로 설계부터 배포까지 전체 과정을 수행해본 경험과, npm workspaces 기반 모노레포로 유저·관리자 페이지를 분리해본 경험이 있어 인프런의 웹 프론트엔드 구조에 빠르게 적응할 수 있다고 판단했습니다. 지식 공유 플랫폼으로서 학습자와 크리에이터 양쪽의 신뢰를 얻어야 하는 인프런 서비스에, 기술적 완성도만이 아니라 "왜 이 기능이 필요한가"까지 함께 고민하는 프론트엔드 개발자로 기여하고 싶습니다.

2. 성장과정 (직무 역량)

저는 말보다 문서로, 추측보다 사실로 팀과 소통하는 방식을 훈련해왔습니다. Kanto 프로젝트에서 외부 멘토가 6주간 20회 넘게 남긴 코드 리뷰가 팀원별로 흩어져 무엇부터 처리해야 할지 불명확해지자, 담당 파일·우선순위·완료 여부를 표로 정리한 리뷰 할당 문서를 직접 만들어 팀 전체가 같은 정보를 보고 판단할 수 있도록 했습니다. 의견과 사실을 구분해 전달하는 습관은 이렇게 만들어졌습니다.

Gentlelion-clone에서도 같은 방식으로 일했습니다. 장바구니에 담은 뒤 상품 가격이 바뀌면 사용자에게 알려야 한다는 필요를 발견했을 때, "알림 기능이 필요하다"고 말로만 전달하지 않고 화면 흐름과 필요한 데이터를 시나리오 문서로 정리해 백엔드에 전달했습니다. 이 문서는 그대로 acknowledge-price API 신설로 이어졌습니다. 타 직군에게 기술적 필요를 설명할 때, 그들이 바로 판단할 수 있는 문서 하나를 만드는 것이 가장 정확한 소통이라고 생각합니다.

3. 성격의 장점과 단점

제 장점은 시키지 않아도 스스로 검증 체계를 만드는 것입니다. Gentlelion-clone에서 기능 구현이 어느 정도 마무리된 뒤, 화면을 눈으로 확인하는 것만으로는 회귀 버그를 놓칠 수 있다고 판단해 로그인·회원가입·장바구니·주문·프로필까지 전체 플로우에 대한 Playwright E2E 테스트를 직접 작성했습니다. 팀장으로서 기능을 나눠 맡기는 데서 그치지 않고, 팀 전체가 안심하고 코드를 고칠 수 있는 안전망을 만드는 것도 제 역할이라고 생각했습니다.

단점은 업무에 대한 몰입도 편차가 크다는 것입니다. 관심이 가는 문제에는 깊이 파고들지만, 반복적이고 정형화된 작업에서는 상대적으로 속도가 떨어지는 경향이 있습니다. 이를 보완하기 위해 반복 작업 자체를 흥미의 문제가 아니라 표준화 신호로 바라보는 방식을 택했습니다. Gentlelion-clone에서 주문·사용자·상품 페이지마다 비슷한 목록·검색 코드를 반복해서 짜야 했을 때, 이 반복을 그냥 참고 넘기는 대신 config와 콜백 기반의 공통 함수(renderRows, search)로 추출해 세 페이지가 재사용하도록 리팩터링했습니다. 흥미 여부와 관계없이 반복이 발견되면 표준화하는 습관으로, 몰입도 편차가 결과물의 품질 편차로 이어지지 않도록 관리하고 있습니다.

4. 입사 후 포부

입사 후에는 인프런의 개발 방식에 맞춰 단계적으로 기여 범위를 넓혀가고 싶습니다. 첫 3개월은 TypeScript·React·Next.js 기반 코드베이스와 모노레포 구조, 팀의 코드 리뷰 문화에 빠르게 적응하는 데 집중하겠습니다. npm workspaces로 유저·관리자 페이지를 분리해본 경험을 바탕으로, pnpm·Turborepo나 Module Federation처럼 더 큰 규모의 모노레포 아키텍처도 무리 없이 학습할 수 있다고 생각합니다.

이후에는 기능을 구현하는 데서 그치지 않고, 제가 맡은 영역만큼은 테스트 코드와 문서로 완결성을 책임지는 개발자로 성장하고 싶습니다. "왜 이 기능을 만드는가"를 먼저 묻고 기획 의도에 맞는 기술적 대안을 제시하며, 팀의 반복 작업을 표준화해 생산성을 높이는 역할을 맡고 싶습니다. 장기적으로는 인프랩이 말하는 존중·탁월성·신뢰·실행의 가치대로, 동료를 먼저 인정하고 사실에 기반해 소통하며 완벽하지 않아도 실행하고 수정해나가는 동료가 되겠습니다.
