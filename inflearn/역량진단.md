# 역량 진단 — 인프런 공고 대비 증명 가능/불가 분석

> 기준 문서: [인프런전략.md](./인프런전략.md)
> 분석 대상: inflearn/resume.html, inflearn/portfolio.html (2026.07 기준)
> 판정 기준: **증명 = 제3자가 확인 가능한 산출물(배포 링크, 저장소, 실측 수치, 문서)이 있는가.** "했다"는 서술만 있으면 증명이 아니라 주장으로 분류.

## 1. 강하게 증명 가능 (수치·산출물·재현 과정까지 있음)

이 영역은 공고 요건과 직접 연결되며, 면접에서 파고들어도 버틸 근거가 있음.

| 역량 | 근거 | 대응되는 공고 항목 |
|---|---|---|
| **성능 병목의 실측 기반 개선** | 마크다운 블록 렌더링: 파싱 0.98ms vs innerHTML 13.45ms로 병목을 실측 특정 → 8.2배 개선. Frontie Lighthouse 48 → PC 92/Mobile 100 (shiki 교체·지연 로딩·memo) | 성능 개선(Lighthouse, code splitting, 번들 최적화) — 인재상 "완결성" |
| **TanStack Query 서버 상태 관리** | useState/useEffect 구조의 중복 GET 문제를 발견하고 도입, 동일 시나리오 재현으로 18회→3회(83.3%) 검증 | 주요업무·우대사항의 TanStack Query 항목과 정확히 일치 |
| **SSR/CSR 구분 적용** | 프로필 페이지 CLS 원인(클라이언트 훅 자체 fetch)을 특정 → 서버 컴포넌트로 데이터 조회 이동, 인터랙션만 클라이언트로 분리 | 자격요건 "SSR/CSR 이해", 주요업무 "SSR/CSR 적절히 선택" |
| **장애 대응 + 재발 방지** | Supabase 트래픽 초과: 원인(원본 이미지 업로드) 특정 → WebP 전환 390MB→64MB(84%) → 동일 조건 재검증으로 재발 없음 확인 | 인재상 "동일 장애 재발 방지를 위한 시스템 개선" |
| **npm 패키지 개발·배포** | markdown-block-preview 실제 npm 공개, 자기 프로젝트에 적용 | 우대 "오픈소스" (단, '기여'가 아닌 '자체 배포' — 2장 참고) |
| **번들러/빌드 이해** | Vite 멀티 페이지 빌드로 MPA 직접 설계, react-syntax-highlighter→shiki 교체로 번들 감량, dynamic import | 우대 "번들러 직접 구성, 빌드 문제 해결" |
| **문서화 습관** | Notion WBS, 주간 팀 보고서 운영(원본 PDF 링크 4종), 기술 블로그에 트러블슈팅 글(티스토리 링크 다수) | 우대 "대화보다 문서", 인재상 "문서화로 지식 공유" |
| **사전 검증(POC성) 사고** | KTS/KPPS 점수 체계를 9개 유저 시나리오로 시뮬레이션해 등급 분포 사전 검증 후 확정 | 인재상 "POC로 검증한 뒤 제안" |
| **실서비스 운영 경험(소규모)** | 블로그 실운영, Kanto 무료→유료 플랜 전환 판단, 관리자 도구(채팅 로그 TXT 증빙) 구축 | 인재상 "본인이 만든 서비스를 실제 운영까지" |
| **TypeScript / React / Next.js 기본기** | 4개 프로젝트 전부 배포 링크 + 저장소 공개 (Kanto는 Next 16, Frontie는 App Router) | 자격요건 핵심 3종 |
| **Git Flow 실운용** | Kanto 저장소 README에 main/develop/release/feature/fix/hotfix 6종 브랜치 전략, 커밋 컨벤션(7타입), PR 승인 규칙(1인 이상 Approve) 문서화. 6주간 커밋 1,191개, 3단계 점진 배포(6/22·7/1·7/6), 핫픽스 2건(결제 웹훅·Storage 트래픽) 실대응 | 자격요건 "Git Flow를 이해하고 계신 분" — release·hotfix 브랜치까지 실제로 운용한 완전한 Git Flow. 단, **이력서·포트폴리오 본문에는 한 줄도 언급이 없어** 심사자가 저장소를 파고들어야만 발견됨 (5장 B 참고) |
| **웹접근성 (WCAG 2.1 AA)** | Kanto 커밋 `5e09252`(PR #169) "WCAG 2.1 AA 기준 접근성 전면 개선": aria-label 18개 파일, aria-expanded/haspopup/pressed, role tab/tablist/tabpanel, time dateTime, dl/dt/dd 구조화, 헤딩 계층 정리, div onClick→Link·img onClick→button 키보드 접근성. `cec93e3`: 모달 role="dialog"·aria-modal·Escape 닫기·포커스 관리. myBlog에도 `8c85e55`(Tab 포커스 복귀 직접 구현)·`5206aa5`(시맨틱·alt·aria-label) | 우대사항 "웹표준·웹접근성" — 포트폴리오의 "WCAG 2.1 AA" 문구는 과장이 아니라 **실증 커밋이 있는 주장**으로 확정. 두 프로젝트에 걸친 일관된 실천이므로 오히려 지금보다 더 구체적으로 표면화할 가치가 있음 |
| **i18n (다국어)** | Kanto에서 본인 커밋으로 확인: "공지사항 국제화", "약관 페이지 다국어(EN/FIL) 지원", "날짜 국제화 개선", "구인구직 i18n 누락 보완", 챗봇 i18n PR 머지 — next-intl 기반 EN/FIL 다국어 실작업 다수 | 우대사항 "i18n 서비스 개발 경험" — "표에 스택만 있고 담당 불명"에서 **본인 담당 확정**으로 승격. 인프런의 i18next·locize(한/영/일/베) 구조와 도구만 다를 뿐 같은 문제를 풀어본 경험. 단 문서 표면에 0회 노출 |

**추상화하면:** 이 지원자의 증명 가능한 정체성은 "**측정 → 원인 특정 → 구조 개선 → 재검증까지 닫는 개발자**"이며, 이는 인프런 인재상의 "시각화로 증명" · "완결성" 축과 정면으로 겹친다. 포트폴리오 표지 컨셉("실측으로 원인을 찾는 개발자")과 실제 근거가 일치함 — 이 축은 유지·강화가 맞다.

## 2. 주장은 있으나 근거가 약함 (서술 1줄뿐이거나, 담당 여부·깊이가 불명확)

면접에서 "구체적으로 어떻게 했나요?"가 들어오면 흔들릴 수 있는 영역. 보강하거나, 보강 불가면 표현 수위를 낮춰야 함.

| 항목 | 현재 상태 | 문제점 |
|---|---|---|
| **반응형 웹** | Kanto 커밋으로 근거 확인: "모바일 공지 배너를 탭 배지 + 모달 방식으로 개선", "모바일 공지 탭 버튼 press 효과 및 헤더 이격 개선" 등 공지사항 영역 모바일 대응 실작업 (+ Frontie Mobile Lighthouse 100 간접 근거) | 근거는 실재하나 자격요건인데 이력서·포트폴리오 어디에도 "반응형" 언급 자체가 없음 — 표면화 필요 |
| **RESTful API 설계** | Supabase API 소비, 레이트리밋 API, Edge Function 프록시 | API를 "사용"한 근거는 많으나 "설계"한 근거는 얇음 |
| **디자인 시스템/공통 컴포넌트** | ESLint-KR CopyableCodeBlock 추출, Kanto "공통 디자인 시스템" 한 줄 | 재사용 컴포넌트 설계 사례는 있으나 소규모. Storybook 등 체계 없음 |
| **모니터링/에러 추적** | Kanto에 Sentry 스크린샷 1장 | Sentry로 실제 에러를 잡아 해결한 스토리가 없음. 인프런은 Datadog 활용을 주요업무로 명시 — "도입해봤다"와 "추적해 해결했다"는 다름 |
| **테스트/자체 검증 체계** | ESLint-KR 주간 스모크 테스트(GitHub Actions) | E2E/유닛 테스트, Storybook 등 인재상이 예시로 든 검증 체계는 없음. 스모크 테스트는 좋은 씨앗이나 홀로 서기엔 약함 |
| **오픈소스 "기여"** | 자체 패키지 배포 + MIT 공개 | 타 프로젝트에 PR/이슈로 기여한 이력은 없음. "오픈소스 기여"로 표현하면 과장이 됨 (현재 이력서의 ESLint-KR "기여" 표현 주의) |
| **타 직군과의 소통** | 군 AOC 업무 체계화 한 줄, 팀 프로젝트는 전원 개발자 | 인프런이 공고·인재상에서 2회 반복 강조한 항목인데, PM/기획/운영과 협업한 직접 근거가 구조적으로 없음 (부트캠프 한계). 군 경험을 "비개발 조직에서의 소통·체계화"로 재해석하는 게 유일한 소재 |
| **AI 도구의 팀 단위 활용** | 주간 보고서 단계별 프롬프팅 사례 | 실제 사례는 있으나 이력서 소개문의 "팀의 개발 기간을 단축" 등 효과 서술에 수치·비교 근거 없음 |
| **모노레포 경험** | [gentlelion-clone](https://github.com/DoHyuk-Centric/gentlelion-clone): npm workspace로 packages/user·admin·share-api(공용 API 패키지) 분리, 앱별 배포 분리, 3인 팀 팀장, 커밋 389개 | **현재 이력서·포트폴리오에 미반영** (클론코딩이라는 이유로 제외). 그러나 모노레포 구조 설계·공용 패키지 추출·배포 분리는 클론 대상이 아니라 본인의 엔지니어링 결정 — 인프런 우대사항(모노레포) 및 주요업무("웹과 모바일이 함께 사용하는 공용 패키지 관리")와 직결되는데 증거가 문서 밖에 방치돼 있음. 단 도구가 pnpm+Turborepo가 아닌 npm workspace라는 차이는 인지 필요 |
| **"왜 만드는가" 비즈니스 관점** | Kanto 문제의식(페이스북 그룹 분산), KTS 필요성 판단 | 방향은 맞으나 "기획 의도에 맞춰 기술 대안 제시" 같은 의사결정 장면으로 정리돼 있지 않고 기능 설명에 묻혀 있음 |

**추상화하면:** 이 영역의 공통 패턴은 "**경험의 씨앗은 있는데 서술이 '스택 한 줄'에 머물러 증거 사슬(무엇을 → 어떻게 → 결과 확인)이 끊겨 있음**". 1장과 같은 실측 서사 구조를 이 항목들에도 적용할 수 있는지가 보강 전략의 핵심.

## 3. 증명 불가 (경험 공백 — 만들어낼 수 없는 영역)

솔직하게 공백으로 인정하고, "학습법"으로 우회 대응해야 하는 영역.

| 공고 항목 | 상태 |
|---|---|
| **React Native / 모바일 앱 개발·배포** | 경험 없음. Android/iOS UI/UX, 네이티브 모듈 연동, 모바일 OS별 트러블슈팅(WebView·영상 플레이어·모바일 OAuth) 전부 공백 |
| **모노레포 (pnpm + Turborepo)** | ~~경험 없음~~ → **2장으로 이동**: gentlelion-clone에서 npm workspace 모노레포 운용 확인. pnpm·Turborepo 자체는 미경험이지만 "모노레포 환경에서 개발해본 경험" 우대 문구에는 해당 |
| **Micro Frontend (Module Federation)** | 경험 없음 |
| **A/B 테스트·기능 플래그 (Hackle류)** | 경험 없음 |
| **사용자 행동 데이터 기반 개선 (Mixpanel·GTM)** | 경험 없음. 프로젝트에 실사용자 트래픽이 사실상 없어 행동 데이터 자체가 존재하지 않음 |
| **Pages Router** | 사용 경험이 App Router(Frontie)·Next 16(Kanto) 중심 — 인프런은 Pages Router 명시. 공백까지는 아니나 차이 인지 필요 |

**추상화하면:** 공백은 전부 "**규모가 있는 실서비스 조직에서만 생기는 경험**"(모바일 앱, 모노레포, MFE, 실사용자 실험)이라는 공통점이 있다. 신입에게 이 공백은 당연하며, 공고 스스로 "몰라도 빠르게 내 것으로 만드는 학습법"을 우대로 열어놨다. 따라서 전략은 은폐가 아니라 — ① 공백을 인지하고 있음을 보여주고, ② 1장에서 증명된 "실측→개선→검증" 학습 사이클을 "나만의 학습법"으로 명명해 이 공백을 메울 방법론으로 제시하는 것.

## 4. 종합 판정

- **정면 승부 축 (그대로 밀 것):** 실측 기반 성능 개선, TanStack Query, SSR/CSR 판단, 장애 재발 방지, 문서화, Git Flow 실운용(Kanto — release·hotfix까지 완전한 형태). 인프런 인재상 4축 중 "시각화로 증명"과 "완결성"은 이미 증거가 갖춰짐. 단 Git Flow는 근거가 저장소 README에만 있고 이력서·포트폴리오 본문에 없음 — 표면화만 하면 됨.
- **보강 축 (증거 사슬 복원 필요):** 접근성·i18n·반응형·모니터링·테스트. 씨앗 경험을 1~2문장 스택 나열에서 "문제→행동→검증" 서사로 승격하거나, 근거를 못 만들면 표현을 낮출 것. 특히 "오픈소스 기여" 표현은 "자체 개발·배포"로 정확히 쓸 것.
- **공백 축 (학습법으로 치환):** RN·MFE·A/B 테스트. 신입 공고이므로 감점 요인이 아니라, "학습법 서사"의 소재로 전환 가능. 단, 자소서/면접에서 아는 척은 금물 — 인프랩 가치의 "사실 기반 보고"와 정면 충돌. (모노레포는 gentlelion-clone 확인 후 공백 축에서 보강 축으로 이동)
- **숨은 자산 1개:** gentlelion-clone(모노레포 + Git Flow형 브랜치 전략 + 팀장). "클론코딩이라서" 제외했지만, 인프런 우대사항과 직결되는 구조 설계 경험이 유일하게 담긴 저장소. UI를 베낀 것과 모노레포 구조·공용 패키지·배포 분리를 설계한 것은 별개 — 후자는 클론이 아니라 본인 결정이므로 반영 가치가 있음.
- **구조적 리스크 1개:** 인프런이 반복 강조하는 "비개발 직군과의 소통"은 현재 자료로 증명 불가능한 유일한 인재상 항목. 군 장교 경험(AOC 체계화)이 유일한 원석이므로, 이걸 "비개발 조직에서 이해관계자에게 상황을 그들의 언어로 보고·체계화한 경험"으로 다듬는 것이 남은 카드.

## 5. 수정·개선 액션 리스트 (우선순위순)

### A. 즉시 수정 — 정확성·과장 제거 (제출 전 필수)

인프랩 가치 "사실 기반 보고"와 충돌하는 표현부터 제거한다. 검증 질문 하나에 무너지는 표현은 강점 열 개보다 위험하다.

- [ ] **resume.html — ESLint-KR "기여" 표현 수정**: "한국 개발자 커뮤니티에 기여하고자 시작"은 유지 가능하지만, 오픈소스 '기여'로 읽히는 굵은 글씨 강조는 제거. "공식 문서에 없는 한국어 가이드를 직접 만들어 공개"로 사실 그대로 기술.
- [ ] **resume.html — 소개문의 근거 없는 효과 서술 수정**: "AI 도구를 역할별로 분리 운용해 팀의 개발 기간을 단축" → 단축 근거(수치·비교)가 없으므로 "보고서·문서화 파이프라인을 자동화해 반복 작업을 줄였다"처럼 증명 가능한 수위로 조정.
- [ ] **portfolio.html — "공통 디자인 시스템 구축 (WCAG 2.1 AA)" 검증**: 실제로 명암비 검사·키보드 내비 등 확인한 내용이 있으면 그 근거를 한 줄 추가하고, 없으면 "WCAG 2.1 AA" 문구 삭제. 접근성은 인프런 우대 항목이라 면접에서 반드시 파고들 지점.
- [ ] **portfolio.html — Kanto 개발환경 표의 next-intl**: 본인이 다국어 처리를 담당하지 않았다면 팀 스택임이 드러나는 현재 위치(표)는 유지하되, 자소서·면접에서 i18n 경험으로 주장하지 않는다고 스스로 선을 그을 것.

### B. 보강 — 씨앗은 있는데 서술이 끊긴 항목 (증거 사슬 복원)

자격요건인데 문서에 아예 없는 항목이 최우선.

- [ ] **반응형 웹 근거 추가 (자격요건인데 언급 0회)**: Kanto·Frontie·블로그 중 실제로 모바일 대응한 화면 하나를 골라, resume 프로젝트 불릿 또는 portfolio에 "모바일/데스크톱 분기 처리" 사례 한 줄 추가. 스크린샷(모바일 뷰) 1장이면 충분.
- [ ] **gentlelion-clone 모노레포 경험 반영 (신규 — 우대사항 직결)**: 클론코딩임을 숨기지 말고 사실대로 쓰되, 강조점을 UI가 아닌 구조 결정에 둘 것. 예: "클론코딩 팀 프로젝트(3인, 팀장) — npm workspace 모노레포로 user/admin 앱과 공용 API 패키지(share-api)를 분리하고 앱별 배포 운영". 이력서에는 프로젝트 목록 하단 1~2줄이면 충분하고, 포트폴리오 타임라인에 넣을지는 지면과 트레이드오프. 인프런 공고의 "공용 패키지 관리" 문구와 연결되는 유일한 경험이므로 자소서 소재로도 확보.
- [ ] **Git Flow 서술을 문서 표면으로 끌어올리기 (자격요건 — 근거는 이미 완비)**: Kanto에서 main/develop/release/feature/fix/hotfix 브랜치 전략과 PR 승인 규칙을 운용했고 핫픽스 2건(결제 웹훅·Storage 트래픽)으로 실서비스 대응까지 한 기록이 저장소 README에 있음. 심사자가 저장소를 열지 않아도 보이도록 포트폴리오 "협업 방식" 슬라이드에 1~2줄(예: "Git Flow 6종 브랜치 운용 · 3단계 점진 배포 · 핫픽스 2건 대응")과 이력서 Kanto 불릿 한 줄로 명시할 것. 특히 "핫픽스 실대응"은 인재상 "완결성"(장애 대응)과도 겹치는 이중 근거.
- [ ] **Sentry 서술 승격 또는 강등**: Sentry로 실제 에러를 잡아 고친 사례가 하나라도 있으면 그 스토리로 교체(인프런 주요업무의 Datadog 항목과 직결). 없으면 "도입"이라고만 쓰고 모니터링을 강점처럼 보이게 두지 말 것.
- [ ] **주간 스모크 테스트를 '자체 검증 체계'로 명명**: ESLint-KR의 CI+주간 스모크 테스트는 인재상 "완결성"의 직접 증거인데 현재 기능 나열에 묻혀 있음. "배포 후에도 스스로 검증 체계를 돌린다"는 프레임으로 승격.
- [ ] **비즈니스 관점 의사결정 장면 1개 발굴**: "왜 이 기능을 만드는가"에 해당하는 실제 판단(예: KTS 도입 이유, 5주차 성능 감사로 범위 조정)을 기능 설명이 아니라 의사결정 서사로 재배치.

### C. 자소서·면접 준비 — 문서 밖에서 채워야 하는 것

- [ ] **공백 스택 대응 답변을 실제 계획 기반으로 재구성 (사용자 피드백 반영)**: "실측 사이클을 학습법으로 명명"하는 추상 서사는 기각 — 지어낸 프레임은 자소서·면접 답변이 될 수 없음. 대신 실제 사실 기반으로:
  - **RN**: Kanto를 실운영하며 유저 유입을 위해 RN 앱 확장을 실제로 계획 중 → "배우겠다"가 아니라 "운영 중인 내 서비스의 필요 때문에 도입을 준비하고 있다"로 답변. 인프런의 웹+RN 앱 구조와 정확히 같은 동기(하나의 서비스를 웹과 앱으로).
  - **모노레포**: gentlelion에서 npm workspace로 경험, 다가오는 해커톤에서 백엔드 담당하며 재사용 예정 → 과거 경험 + 현재 진행형 계획으로 답변 가능.
  - **MFE(Module Federation)**: 실제로 모르는 개념 → 아는 척 금지. "개념 학습이 필요한 영역"으로 정직하게 두고, 면접 전 개념만 파악(여러 팀이 각자 빌드·배포하는 프론트엔드 조각을 런타임에 하나의 앱으로 합치는 아키텍처. 인프런이 독립 배포를 위해 사용).
  - 단, "예정·계획"은 증명이 아니므로 이력서·포트폴리오에는 쓰지 않고 자소서·면접 답변으로만 사용. (자소서 작성 시 Introduction.md 가이드 준수)
- [ ] **군 AOC 경험 재서술**: "비개발 조직에서 이해관계자에게 그들의 언어로 보고하고 업무를 체계화한 경험"으로 다듬어, 증명 불가였던 '비개발 직군 소통' 항목의 답변 카드로 준비.
- [ ] **Pages Router 차이 학습**: 경험이 App Router 중심이므로 Pages Router와의 차이(라우팅, 데이터 페칭 getServerSideProps 등)를 정리해 "차이를 인지하고 있다"는 답변 준비.
- [ ] **모르는 스택 아는 척 금지 원칙 확정**: MFE·A/B 테스트는 "경험 없음 + 이렇게 배우겠다" 구조로만 답변. 모노레포는 "npm workspace로 운용해봤고 pnpm+Turborepo는 미경험 — 차이는 이렇게 이해하고 있다"로 정확히 답변. 인프랩 가치 "사실 기반 보고"에 부합하는 태도 자체가 가점.

### D. 선택 투자 — 시간이 남을 때만 (제출 일정과 트레이드오프)

- [ ] gentlelion-clone을 pnpm workspace + Turborepo로 마이그레이션해보는 반나절 POC → "npm workspace 경험을 인프런 스택으로 스스로 확장했다"는 학습법 실증 사례가 됨 (기존 '미니 모노레포 신규 구축' 항목을 대체 — 이미 있는 자산을 확장하는 쪽이 비용 대비 서사가 강함).
- [ ] 접근성 실측 1회(Lighthouse 접근성 점수 + axe 스캔)를 돌려 수치를 확보하면 A항목의 WCAG 문구를 삭제 대신 근거로 전환 가능.
- [ ] 블로그·ESLint-KR에 간단한 사용자 지표(방문 수 등)가 있다면 "데이터 기반 개선" 공백을 부분적으로 메울 소재로 검토.
