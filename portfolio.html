03. Project — Kanto · Details (2/4)

경험

프로필 페이지 · 칸토 망고 점수

당근온도처럼, 신뢰가 핵심인 서비스엔 신뢰도를 판단할 시각적 기준이 필요하다고 판단해 KTS(신뢰도)·KPPS(인기도)를 설계했습니다. 리뷰 평점·거래 완료·계정 활동 등 5개 요소를 배치 함수로 합산해 A~E 등급의 "망고 지수"로 시각화하고, 유형별 인기 게시물 상위 5개엔 자동으로 배지를 부여합니다.

매일 KTS 03:00·15:00 → KPPS 03:30·15:30 순서로 pg_cron 자동 재계산합니다.

시나리오를 세워서 유형별 예상 KTS·등급 분포를 미리 그려보며 기준을 조율했습니다.

KTS 등급×참여도 조합별 KPPS 값과 분포까지 시뮬레이션해 인기글 기준(상위 5개)을 설계했습니다.

채팅 · 관리자 채팅 로그

유저 간 원활한 소통을 위해 Supabase Realtime 기반 1:1 채팅을 전체 구현했고, 여기서 발생할 수 있는 법적 분쟁이나 사용자 문의에 대응할 수 있어야 한다고 판단해 관리자가 신고된 채팅방의 대화 내역을 페이지네이션으로 조회·다운로드할 수 있는 관리 도구까지 구축했습니다.

관리자 채팅 상세 드로어 - 참여자별 탭으로 나눠 채팅 로그를 빠르게 조회할 수 있습니다.

다운로드된 TXT 파일 - 채팅방 ID·참여자·게시글 정보까지 포함해, 분쟁 발생 시 바로 증빙 자료로 활용할 수 있습니다.

관리자 운영관리 · 관리자 권한 체계

관리자/유저로만 나뉘는 체계는 너무 단순했고, 관리자를 등록·제거할 때마다 매번 DB에 직접 접근해야 하는 방식은 서비스를 운영하는 입장에서 불편할 것이라 판단했습니다. 그래서 팀 단위로 권한을 묶고 어드민 → 슈퍼어드민 승격까지 UI에서 처리할 수 있는 권한 체계와, 대시보드 KPI·신고 관리·감사 로그 등 운영관리 페이지 전체를 설계·구현했습니다.

팀 목록 - DB 접근 없이 UI에서 팀 단위 권한 관리·승격이 가능해졌고, 처리 이력은 감사 로그로 남아 추적할 수 있습니다.

어드민 추가 - 유저명 검색만으로 팀에 배정하면 권한이 자동 적용돼, DB 접근 없이도 관리자 등록·제거가 가능합니다.

03. Project - Kanto · Details (3/4)

문제해결

Supabase 트래픽 한도 초과 대응

기획 단계에서 무료 플랜의 트래픽·토큰 한도를 미리 계산해 소진 시나리오와 대응 전략을 세워뒀지만, 실제로는 예상 밖의 지점에서 문제가 터졌습니다.

7/1 Storage Egress 390MB(전체 88.7%) 급증 → WebP 전환 후 재발 없음

  • 이미지를 WebP로 사전 전환해두지 않은 상태에서, 시연 준비 중 봇 계정과 목업 이미지를 대량 등록하다 Supabase 트래픽 한도 초과가 발생했습니다.
  • 사전에 세워둔 대응 전략 덕분에 당황하지 않고 원인을 빠르게 추적했고, 원인은 이미지 용량이 트래픽에 미치는 영향을 원인으로 특정했습니다.
  • 부계정 이전 대신 유료 플랜 전환으로 즉시 정상화하고, WebP 전환 로직을 중간단계로 추가 후 동일 조건으로 이미지를 올려도 트래픽이 안정적임을 확인해 재발 방지까지 검증했습니다.

내 프로필 페이지 — 서버/클라이언트 컴포넌트 분리

프로필 페이지를 처음 구현할 때는 로그인·회원가입 페이지가 아직 구현되기 전이라, 빠른 개발을 위해 목업 데이터를 쓰는 클라이언트 컴포넌트로 만들었습니다. 이후 Supabase API로 실제 데이터를 연결하고 소셜 로그인 "연결하기/연결됨" 버튼과 관심 카테고리를 구현하는 과정에서, 처음엔 안 보이다가 뒤늦게 나타나는 CLS(레이아웃 시프트) 현상이 생겼습니다.

  • 원인은 각 섹션이 클라이언트 훅에서 자체적으로 데이터를 불러오던 구조였기 때문이었습니다. 페이지가 먼저 빈 상태로 그려지고, 그 다음 브라우저에서 데이터를 요청해오니 버튼·카테고리가 한 박자 늦게 나타난 것이었습니다.
  • 페이지 전체를 서버 컴포넌트로 두고, 필요한 데이터를 서버에서 미리 불러와 완성된 상태로 클라이언트에 내려주는 구조로 전환했습니다. 클라이언트 훅은 자체 fetch 로직을 걷어내고, 서버가 준 초기값만 받아쓰도록 단순화했습니다.
  • 이후 페이지가 복잡해지면서(리뷰·모임·활동 통계 등) 늘어난 기능들도 같은 원칙을 유지해, 데이터 조회는 서버 컴포넌트에 모으고 인터랙션만 클라이언트 컴포넌트로 넘기는 구조를 끝까지 지켰습니다.

04. Project — myBlog · Details (2/2)

경험 및 문제해결

markdown-block-preview · 자체 npm 패키지

마크다운 에디터에서 입력할 때마다 미리보기 전체를 다시 렌더링하면 글이 길어질수록 타이핑이 버벅였고, 실측해보니 병목은 재파싱이 아니라 DOM 트리 재구성 비용이었습니다. 빈 줄 기준으로 문서를 블록 단위로 나눠 바뀐 블록만 DOM에 반영하는 방식을 설계했고, 마땅한 라이브러리가 없어 npm 패키지로 직접 만들어 배포했습니다.

별도 저장소로 분리 개발해 npm에 배포, 이 프로젝트의 글쓰기 에디터에 그대로 적용했습니다.

초기 렌더링 흐름 - 블록 분리 → 블록별 DOM 요소 생성 → 초기 화면에 커밋하고 다음 비교 기준(prevBlocks)으로 저장합니다.

입력 시 갱신 흐름 - 블록 수가 같으면 바뀐 인덱스만 교체, 끝에만 추가됐으면 한 블록만 붙이고, 그 외엔 전체를 다시 그립니다.

이미지 지연 업로드 패턴

처음엔 이미지를 선택하는 즉시 Storage에 업로드했는데, 임시저장 없이 중간에 나가버리면 쓰이지 않는 이미지가 Storage에 그대로 쌓이는 문제가 있었습니다.

  • 그래서 발행 시점에만 실제 업로드하도록 바꿨는데, 그 전까지 미리보기는 어떻게 보여줄지가 새로운 문제였습니다.
  • URL.createObjectURL()로 만든 blob: 임시 주소로 해결했습니다 — 파일을 선택하면 브라우저가 그 파일을 가리키는 로컬 주소를 즉석에서 만들어 미리보기에 쓰고, 실제 파일은 별도 Map에 그 주소와 함께 잠깐 담아뒀습니다.
  • 발행 버튼을 누른 시점에만 이 주소들을 찾아 실제로 업로드하고, 마크다운 속 주소를 진짜 업로드된 주소로 바꿔치기해 불필요한 업로드와 고아 이미지 발생을 줄였습니다.

인증 수단 일원화 — Firebase → Supabase

게시글·프로필 DB는 Supabase Postgres로 쓰기로 했는데, 인증은 먼저 붙여둔 Firebase를 그대로 쓰고 있어 공급자가 이원화돼 있었습니다.

  • Firebase Auth의 사용자 식별자와 Supabase의 user_id 외래키를 정합성 있게 묶기 어렵고, 인증과 데이터가 분리돼 있으면 RLS(행 단위 보안)로 소유권을 강제할 수 없다는 게 원인이었습니다.
  • 인증까지 Supabase Auth(GitHub·Google OAuth)로 일원화하고, Firebase는 인증 레이어에서 완전히 제거했습니다.
  • checkPostOwner가 현재 로그인한 사용자의 id와 게시글의 user_id를 직접 비교하는 방식으로 소유권 검증을 구현·검증 했습니다.
